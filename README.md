# db-sanitizer — санитизация PostgreSQL-баз

Инструмент обезличивания производственных баз данных для передачи копий за пределы прод-контура: в среды разработки и тестирования, аналитикам, внешним подрядчикам. Ответ на тестовое задание РУСАЛ.

Полный проектный документ с обоснованием каждого решения — **`docs/solution-design.md`**. Проект прошёл **пять структурных разборов** (`docs/design-review*.md`): внутренняя целостность ×2, соответствие ТЗ и законодательству по официальным публикациям, разбор реализации против контрактов, разбор результата правок. Четвёртый и пятый нашли реальные утечки персональных данных в копию — оба закрыты, оба сопровождены проверками, которые поймали бы их снова. Состояние по модулям и стадиям V-модели — `docs/module-status.md`.

## 1. Формат решения и обоснование

**Репозиторий** с контейнеризированной утилитой (CLI): `docker compose` поднимает демо-Postgres, staging-Postgres и контейнер инструмента; полный цикл — одна команда `make demo`. Формат выбран вместо стенда, чтобы проверяющий воспроизводил результат локально и видел код.

Центральная идея: **санитизация — это компилятор, а не скрипт**. LLM-агенты работают на метаданных в редкой «фазе планирования» и производят ревьюируемый артефакт — `sanitization-plan.yaml`. Исполнение — детерминированный конвейер без LLM в горячем цикле, двумя проходами:

- **проход 1** — Greenmask выгружает дамп, наш Cmd-трансформер заменяет структурные колонки на потоке `COPY` (источник только читается);
- **проход 2** — обвязка дообрабатывает свободнотекстовые таблицы поверх готового дампа (NER + правиловый страховочный слой + локальная LLM на неуверенных фрагментах с версионируемым кэшем) и кладёт внутрь дампа схему `sanitization` с примечаниями о деградациях.

## 2. Open-source компоненты и внесённые доработки

| Компонент | Роль | Наша доработка |
|---|---|---|
| **Greenmask** (Apache-2.0, версия зафиксирована в Dockerfile) | движок исполнения: потоковая трансформация при `pg_dump`, directory-формат, параллелизм | генерация `config.yml` из плана; `Cmd`-трансформер с русской семантикой; признанные ограничения (вход-дамп через staging, дозапись схемы — SQL-компаньоном) |
| **LangGraph** (MIT) | оркестрация фазы планирования | граф profiler → classifier → policy → FK-замыкание → corpus → **человеческий гейт** (`interrupt` + checkpointer) |

| **spaCy/Natasha** (MIT) | NER для свободного текста (прод) | в демо — словарный NER (словарь ФИО источника, живёт в контуре) + правиловый слой; spaCy подключается конфигом |

Правиловые распознаватели российских идентификаторов (ИНН/СНИЛС/ОГРН — контрольные суммы; паспорт/КПП — формат + контекстные якоря) написаны свои: в готовых наборах их нет.

## 3. Механика замен, в том числе сквозных

Ключевая формула: `fake = corpus[ SHA3(salt ‖ normalize(src)) mod |corpus| ]`.

- **Сквозная консистентность** — по построению: одно исходное значение даёт одну замену во всех таблицах и в свободном тексте, без таблицы соответствий и общего состояния. Ключ — «личность», не строка: ФИО нормализуется покомпонентно с грамматическим родом («Петров Иван Иванович», «ПЕТРОВА А.И.» и «Петров» в комментарии дают согласованные замены).
- **Уникальность** (`UNIQUE`-колонки) — структурной генерацией: тело идентификатора проходит формат-сохраняющую перестановку (4-раундовый Фейстель поверх SHA3 — биективна, коллизии исключены математически), контрольная сумма досчитывается. ИНН/СНИЛС/ОГРН валидны для приложений.
- **Соль производная**: `HMAC(master[v], получатель ‖ поколение)` — копии разных получателей несвязываемы, внутри копии всё воспроизводимо; версия соли пишется в журнал прогона.
- **Стратегии по приказу РКН №140**: `direct`/`fake`/`generate` (введение идентификаторов, п. 2), `generalize` (п. 4/п. 12), `shuffle` (перемешивание, п. 10 — предвычисленная перестановка), `keep`, `null`. Соответствие сверено с официальной публикацией приказа (см. §6.1 проектного документа).
- **Fail-closed**: колонка вне плана роняет прогон; `unresolved` блокирует валидацию; ПДн-тип в прямом LLM-режиме — ошибка валидации; jsonb без разметки ключей не исполняется; нераспознанный хвост грязного адреса не сохраняется.

## 4. Способ использования LLM

Два режима по осям «чувствительность × кардинальность» (ТЗ требует LLM-генерацию замен; ограничение безопасности — настоящие ПДн модели не показываются):

- **Прямой** (не-ПДн, ≤10 000 уникальных: названия контрагентов, проектов) — LLM видит список уникальных значений и порождает замену 1:1; материализуется в план, проходит человеческий гейт. Буквальное выполнение требования ТЗ.
- **Корпусный** (ПДн любой кардинальности) — LLM порождает взвешенные компоненты (фамилии, имена, улицы), корпус собирается комбинаторно; привязка — детерминированный хэш. LLM не видит ни одного настоящего значения.
- **Свободный текст** — NER первым эшелоном, локальная LLM (Ollama, в контуре) только на фрагментах ниже порога уверенности, с кэшем по хэшу текста (кэш — версионируемый артефакт, условие воспроизводимости).
- В CI и демо LLM-ответы — записанные фикстуры: конвейер детерминирован и работает без сети.

### Как подключается модель

Поставщик задаётся окружением и **опционален**: без него конвейер идёт по записанному кэшу голосов и поставляемым словарям — проверяющий воспроизводит прогон, не поднимая модель.

```bash
# локальная модель в контуре (все четыре роли)
export LLM_PROVIDER=ollama LLM_MODEL=qwen3:8b
# любой OpenAI-совместимый API (роли 1-3; свободный текст ему не показывается)
export LLM_PROVIDER=openai LLM_BASE_URL=https://api.example LLM_API_KEY=...
make demo
```

**Граница безопасности проведена в коде, а не в инструкции.** Роль 4 (третий эшелон NER) — единственная, где модель видит живой текст с персональными данными, и она допускает только поставщика в контуре (`localhost`, `host.docker.internal`, `ollama`). Внешний API на этой роли получает отказ `LLMUnavailable`, а не предупреждение. Роли 1–3 персональных данных не видят по построению: классификатор получает только метаданные, генератор корпусов порождает значения с нуля, карта 1:1 работает с колонками, признанными не-ПДн.

Измерено на демо-схеме (69 колонок, `qwen3:8b` на CPU):

| | без модели | с моделью |
|---|---|---|
| Неразобранные фрагменты свободного текста | 88 | **0** |
| Голос классификатора | из записанного кэша | 69 колонок, 51 с определённым типом |
| Обращений к модели за прогон | 0 | 88 (`direct`, `ner`) |

Качество второго голоса на восьмимиллиардной модели — **7 из 8** на путающих случаях (суррогатные ключи, даты, категориальные коды); без правил в системном промпте модель размечала как «табельный номер» **все** колонки `*_id`. На СНИЛС модель воздержалась — и это правильно: там правила берут значение контрольной суммой с уверенностью 1.0. Голоса дополняют друг друга ровно там, где задумано.

## 5. Архитектура и масштабируемость

```
ПЛАНИРОВАНИЕ (LLM, редко)          ИСПОЛНЕНИЕ (без LLM, каждый прогон)
profiler → classifier ⇄ rules      проход 1: Greenmask + Cmd (COPY-поток)
        → policy → FK-замыкание    проход 2: текст+схема sanitization поверх дампа
        → corpus → ЧЕЛОВЕЧЕСКИЙ    verify: restore в staging, канарейки,
          ГЕЙТ (interrupt) → план  fake(x)≠x, энтропия, консистентность → run_log
```

- **Масштаб**: LLM вне горячего пути; поток `COPY` без материализации (исключение — предвычисленные перестановки `shuffle`); параллелизм Greenmask; `subset` для подмножеств. Демо-масштаб параметризован (`--scale small|medium|large`).
- **Расширяемость**: ядро `detect → decide → map → apply`; для файловых источников (docx/csv) переиспользуются корпуса, соль и правило отображения — тот же человек получит тот же псевдоним в базе и в документе.
- **Эксплуатация командой**: план в git через pull request; журнал прогонов с версиями плана/соли/корпуса/кэша; дамп не публикуется до завершения верификации; примечания о деградациях едут внутри копии (схема `sanitization`).
- Модули и границы — `.grace/` (проект ведётся по GRACE 4); статус — `grace status --path .`.

## Запуск

Требования: Docker (compose v2), `make`. Всё остальное — в контейнерах.

```bash
# полный цикл: посев демо-базы → план с гейтом → два прохода → restore → верификация
make demo
# отчёт «до/после»: out/verify-report.md

# вход «дамп» по ТЗ: pg_dump → временная БД → тот же конвейер
make demo-dump

# юнит-тесты (без Postgres и LLM)
make test
```

Интерактивный гейт (вместо автоаппрува): `python -m sanitizer.cli plan` без `--auto-approve` — конвейер остановится, покажет черновик плана, дифф и блокеры; решения задаются в `sanitizer/demo/plan-config.json` (`overrides` — это и есть зафиксированные решения человека).

Соль и получатель: переменные окружения `MASTER_SALT`, `RECIPIENT`, `GENERATION`, `MASTER_SALT_VERSION`. Копии двух получателей несвязываемы (проверяется e2e-тестом).
