# Разбор 5: результат правок

Первые три разбора проверяли замысел, четвёртый — реализацию. Этот проверяет **результат работы по четвёртому**: закрылись ли находки на самом деле, не появилось ли новых дыр, и — главное — честны ли утверждения, которые проект делает о себе после правок.

Метод: чтение кода против контрактов и документов, затем независимая проверка каждого утверждения — исполнением кода, запросом к живым базам и к опубликованному дампу. Дата: 2026-07-31.

---

## Вердикт

Четыре ранга закрыли то, что было названо, но не то, что было заявлено. **Опубликованная копия содержала персональные данные в момент, когда отчёт верификатора был зелёным по всем девяти строкам**: 783 СНИЛС с валидной контрольной суммой в свободном тексте, 374 из них дословно совпадали с исходными записями сотрудников.

Причина не в новой правке. Страховочный слой прохода 2 опознавал идентификаторы **по пунктуации**: СНИЛС — только с дефисами (`123-456-789 64`), ИНН — только в 10 и 12 цифр. База пишет СНИЛС подряд (`09085653089`), и такие значения не видел никто. Канарейки этого не поймали, потому что канареечная запись была написана с дефисами; враждебные случаи ранга 3 — потому что добавляли новые формы, а не новые *написания* старых.

Это тот же сорт ошибки, что и в разборе 4, на уровень выше: там тесты проверяли код на данных, подобранных так, чтобы он работал; здесь **проверки проверяли ровно те форматы, которые обработчик умеет**. Проверка, унаследовавшая слепоту проверяемого, ничего не доказывает.

## Находки

### 1. Утечка: СНИЛС без разделителей проходил свободный текст насквозь

```python
postproc.py:38  _SNILS_RE = re.compile(r"(?<!\d)\d{3}-\d{3}-\d{3}[\s-]?\d{2}(?!\d)")
postproc.py:39  _INN_RE   = re.compile(r"(?<!\d)\d{10}(?:\d{2})?(?!\d)")
```

Проверено запросом к копии и к каталогу `out/published`:

```
СНИЛС с валидной КС в тексте копии:            783
из них совпадают с hr.employees.snils:          374
```

Тикет в staging: «Сверьте СНИЛС **91789490072** в личном деле». В источнике это СНИЛС сотрудника `id=3`, чья структурная колонка в копии заменена. Копия несла мост «настоящий СНИЛС → псевдонимизированная запись» — то есть обезличивание было обратимо без ключа.

**Исправлено.** Идентификатор в тексте опознаётся **контрольной суммой**, а не пунктуацией: любая последовательность 10–15 цифр проверяется на ИНН, СНИЛС и ОГРН и заменяется тем же генератором, что и структурная колонка. Число без валидной КС (номер заявки, инвентарный номер) не трогается. Телефоны заменяются раньше и исключены лидирующим `+`.

**Как проверено после правки:** тот же запрос даёт `0`. Тесты: замена СНИЛС в четырёх написаниях, ИНН и ОГРН в тексте, неприкосновенность числа без КС, отсутствие двойной замены телефона.

### 2. Проверка, которая ловит этот класс без канареек

Дыра была не в регулярном выражении, а в том, что **ни одна из девяти проверок не сравнивала копию с источником по существу**. Канарейки покрывают 11 заранее известных значений; всё остальное держалось на честном слове обработчика.

**Добавлена проверка:** все значения ИНН/СНИЛС/ОГРН источника собираются в множество, копия сканируется по всем текстовым колонкам, найденные цифровые последовательности сверяются по нормализованному виду. Проверка не наследует слепоту прохода 2, потому что опознаёт по контрольной сумме, а не по формату.

### 3. Пропущенная проверка засчитывалась пройденной

```python
verifier.py:45  return all(c.passed for c in self.checks if not c.skipped)
```

На чужой базе без описанных проб две проверки консистентности помечались пропущенными, `report.ok` оставался `True`, журнал получал `done`, публикация разрешалась. Метка ⏭ была честной, но ни на что не влияла. **Исправлено:** непроведённая проверка блокирует публикацию; метка осталась, чтобы отличать «не проверяли» от «проверили и упало». Проверка целостности текста при отсутствии проб раньше просто исчезала из отчёта — теперь помечается пропущенной.

### 4. Деградации прохода 2 фиксировались и ничего не значили

`sanitization.summary` в копии: 88 фрагментов свободного текста оставлены без изменений (`low_confidence_ner`). Ни верификатор, ни гейт публикации этих чисел не читали.

**Исправлено:** допустимое число деградаций объявляется планом (`params.max_degraded`), проходит человеческий гейт и проверяется верификатором. Без объявленного порога верификация не проходит: молчаливое умолчание здесь означало бы, что неразобранный фрагмент уезжает в копию без единого следа.

### 5. Разнообразие: обещание, которого корпус не может выполнить

Проверка «просадка энтропии ≤10%» сравнивала копию с источником. Замена из корпуса размера *m* по хэшу даёт в среднем *m·(1−e^(−n/m))* различных значений: при 80 женских именах в корпусе и сотнях исходных имён просадка **неизбежна физически**. Прежний зелёный результат был везением конкретной соли — смена соли сделала проверку красной без единого изменения в логике замен.

**Исправлено:** порог применяется к достижимому разнообразию, а отчёт называет колонки, где предел задан корпусом, и сам предел:

```
| Разнообразие: просадка энтропии <= 10% от достижимого | ✅ |
  ограничено корпусом: hr.employees.first_name (потолок 6.31),
  hr.employees.last_name (потолок 7.75), hr.employees.middle_name (потолок 7.27) |
```

Это не смягчение критерия, а прекращение обещания, которое нечем обеспечить. Расширение корпусов — отдельная работа с внешним источником имён.

### 6. Первичный ключ по-прежнему угадывался как колонка `id`

```python
executor.py:219      columns = [{"name": "id", "not_affected": True}] ...
cmd_transformer.py:215  ap.add_argument("--pk", default="id")
postproc.py:237      pk = fields[0]
```

Находка 15 разбора 4 была закрыта только в верификаторе. На таблице с ключом `pay_no` конфиг Greenmask запрашивал несуществующую колонку; примечания прохода 2 ключевались первой колонкой файла — а ею могут быть персональные данные, которые так попадали бы в `sanitization.notes`, то есть в копию.

**Исправлено:** первичные ключи едут в самом плане (`Plan.primary_keys`), заполняются из снимка схемы, проходят гейт вместе с остальными решениями. Тест построен на таблице с ключом, который не называется `id`.

### 7. Бесконечный цикл при исчерпании карты 1:1

```python
executor.py:65  while fake in used: i += 1; fake = f"{base}-{(...) % 997}"
```

Суффикс по модулю 997 даёт не более 997 форм на одну базу; при исчерпании цикл не завершался ни ошибкой, ни таймаутом. Воспроизведено на корпусе из двух значений: на 1970-м источнике прогон уходит в вечное ожидание. **Исправлено:** цикл ограничен, исчерпание — явная ошибка с указанием, что делать.

### 8. Мелкие правки того же сорта

| Что | Было | Стало |

## Что осталось незакрытым — осознанно

- **LLM отсутствует физически** во всех четырёх заявленных ролях; **Presidio заменён** своими правилами. Записано отклонениями в `requirements.xml`, `§4.2` и `§4.3` проектного документа.
- **Человеческий гейт не имеет входа из CLI.** Чекпойнтер графа живёт в памяти процесса, поэтому продолжить прогон после `interrupt` из другой команды нельзя: `resume_approved` вызывается только тестами. Единственный рабочий путь — `--auto-approve` со списком `confirm` в конфиге, и такое подтверждение помечается `ci`, а не `human`. Различие видно в плане, но `validate_plan` его не требует. Закрыть можно переносом чекпойнтера в SQLite — отдельная работа.
- **Валидация (столбец «Влд») не начиналась**: на копии никто не работал.
- **Демо-специфика `report.py`** (выборки по `hr.*`) оставлена: страница стенда демонстрационная по назначению.
- **Расширение корпусов** до размера, снимающего потолок разнообразия, требует внешнего источника имён — Faker ru_RU отдаёт 250 фамилий и 80 женских имён, это его потолок.

## Разрешения противоречий — состояние

| Противоречие | Состояние | Чем проверено |
|---|---|---|
| Подтверждение только на гейте ↔ пустой дифф при неизменной схеме | разрешено | повторный прогон даёт пустой дифф; удаление `confirm` из конфига блокирует план |
| `direct` без LLM ↔ запрет `fake` на низкой кардинальности | разрешено | карта 1:1 строится корпусом, `llm_mode` называет автора; 61 контрагент → 61 уникальная замена |
| Fail-closed ↔ исполнимость демо | разрешено смещением решений в конфиг | демо идёт только с `--auto-approve` и заранее заполненными `overrides`/`confirm`; человека на гейте нет ни в одном сценарии `Makefile` |
| Разнообразие ↔ конечный корпус | разрешено сужением обещания | порог применяется к достижимому, потолок назван в отчёте |

## Главный вывод

Разбор 4 показал, что тесты проверяли код на удобных данных. Разбор 5 показывает уровнем выше: **проверки проверяли те же форматы, которые умеет обработчик**. Канарейка, написанная тем же способом, что и обрабатываемое значение, доказывает работоспособность обработчика на самом себе.

Отсюда правило, которое стоит держать дальше: проверка не должна использовать тот же признак, что и проверяемый механизм. Обработчик опознаёт по формату — проверка обязана опознавать по контрольной сумме. Обработчик знает список канареек — проверка обязана сравнивать множества целиком. Проверка, которую нельзя провести, обязана блокировать, а не молчать.

Итог прогона после правок: **163 теста**, одиннадцать проверок верификатора, ноль идентификаторов источника в копии.
