# Разбор 4: код, архитектура, пользовательские истории

Первые три разбора проверяли **замысел**. Этот проверяет **реализацию**: делает ли код то, что обещают контракты; держит ли архитектура заявленные свойства; складывается ли из 15 модулей работающее целое.

Метод: разбор всех ~3500 строк кода против контрактов и проектного документа, затем независимая верификация каждой находки — цитатой с номером строки, исполнением кода или экспериментом на живой БД. Дата: 2026-07-31.

**Из 12 проверяемых находок снято 0, скорректировано 5, подтверждено 12. Плюс 5 не заявленных найдено при верификации.**

---

## Вердикт

Код в основном соответствует контрактам, но **пять контрактов содержат прямую неправду, и три из них — про безопасность**. Архитектурные свойства держатся на демо-базе и рассыпаются на реальной. Главное: **демо-база устроена так, что не содержит ни одного случая, ломающего код** — нет 10-значных ИНН, табельные лежат в одном окне, нет ИНН в свободном тексте, нет лишних ключей в jsonb, нет обратных слэшей в тексте, нет связи между зарплатой и начислениями. Отсюда 103 зелёных теста при пяти дефектах порчи данных и четырёх путях утечки.

Самое неприятное: **все три пути утечки невидимы для всех восьми проверок верификатора одновременно** — именно по ним утечка и произойдёт на незнакомой базе.

## P0. Утечка ПДн мимо всех проверок

### 1. Первичный ключ отменяет оба голоса классификатора

`classifier.py:176-177` — **первая** ветка `classify`, до сведения голосов:

```python
if col.is_pk or (col.data_type in ("integer", "bigint") and col.name.endswith("_id")):
    out.append(ClassifiedColumn(col.qualified, SemType.TECHNICAL, 1.0, False, "pk/fk"))
```

Результаты `rules_detect` и голоса LLM вычислены строками выше и молча выброшены. Эксперимент на живой БД:

```
exp3.users.email  is_pk=True  rules_detect=(SemType.EMAIL, 1.0)   ← правила уверены на 100%
exp3.users.email  sem_type=technical reason=pk/fk                  ← classify игнорирует
exp3.users.email  strategy=keep                                    ← в план: не трогать
```

Естественный ключ-ПДн — обычная практика: `PRIMARY KEY (email)`, `PRIMARY KEY (snils)`, `PRIMARY KEY (inn)`. Составной ключ `(last_name, first_name, birth_date)` отправит в `keep` все три колонки.

**Правильно:** `is_pk` — сигнал «нельзя менять без сохранения уникальности», а не «это не ПДн». Ключ-ПДн должен идти в `generate` (биективная замена в mapper уже есть) или в `unresolved`.

### 2. Ложный первичный ключ из-за неполного join

`profiler.py:98-103` соединяет `table_constraints` с `key_column_usage` по имени ограничения и схеме, **без имени таблицы**. Имя таблицы берётся из одной части, имя колонки — из другой; при совпадении имён они разъезжаются.

Уточнение по итогам эксперимента: два одноимённых PK/UNIQUE в схеме невозможны — Postgres откажет на уровне имени индекса. **Реальный путь — FK, названный так же, как PK другой таблицы** (FK индекса не создаёт):

```
('exp5.a', 'id',    'PRIMARY KEY')
('exp5.a', 'a_id',  'PRIMARY KEY')   ← колонки a_id в таблице a нет, строка-фантом
```

Складывается с находкой №1:
```
exp5.a.email  is_pk=True (ложно)  samples=['user10@rusal.ru', ...]
exp5.a.email  sem_type=technical reason=pk/fk
```

На базе, где имена ограничений генерит ORM (`fk_user`, `uq_code`), совпадения ожидаемы. Чинится добавлением `AND kcu.table_name = tc.table_name`.

### 3. Неразмеченный ключ jsonb проходит насквозь, и это невидимо для fail-closed

**Половина А.** `cmd_transformer.py:152` итерирует по разметке, а не по данным. Прогон:

```
phone       '+79161234567'            -> '+79772982660'
emergency   'Иванов Пётр Сергеевич'   -> 'Гришин Софон Чеславович'
snils       '112-233-445 95'          -> '112-233-445 95'          ← НЕ ТРОНУТ
passport    '4509 123456'             -> '4509 123456'             ← НЕ ТРОНУТ
spouse_fio  'Иванова Мария Петровна'  -> 'Иванова Мария Петровна'  ← НЕ ТРОНУТ
```

Для колонок политика «не знаем → `unresolved`», для ключей jsonb — «не знаем → отдать как есть». Прямое противоречие принципу.

**Половина Б.** `schema_fingerprint` (`policy.py:74-76`) считается по `qualified:data_type` и **не включает `json_keys`**, хотя профайлер их собирает:

```
fingerprint без snils/passport: f867515e7c173f7e
fingerprint С  snils/passport : f867515e7c173f7e   ← совпадают
validate_plan против новой схемы: ОШИБОК НЕТ
```

Разработчик добавил в jsonb ключ `passport` — дрейф не сработал, гейт молчит, прогон «зелёный», паспорт уехал в staging.

### 4. Человеческое подтверждение подделывается неподписанным JSON

`plan_graph.py:71-74` применяет `overrides` через `setattr` без белого списка. Источник — обычный `plan-config.json`. Прогон с враждебным конфигом:

```
ДО   : email strategy=generate | snils strategy=generate | birth_date confirmed=False
ПОСЛЕ: email strategy=keep     | snils strategy=keep     | birth_date confirmed=True
       + произвольный новый атрибут (dataclass без __slots__)
validate_plan ошибок по подмене: 0
```

**Усугубляющее обстоятельство, найденное при верификации:** `confirmed` **нельзя** проставить на самом гейте. `resume_approved` (`plan_graph.py:132`) отправляет `{"approve", "confirm"}`, а `_node_gate` (`plan_graph.py:92`) читает только `approve`; `confirm` не читается нигде. Единственный работающий канал «человеческого подтверждения» — тот самый неподписанный JSON. **Гейт не сужает поверхность атаки, он её создаёт.** Комментарий `policy.py:45` («проставляется на гейте») не соответствует коду.

## P1. Порча данных

### 5. Все 10-значные ИНН получают невалидную контрольную сумму

`cmd_transformer.py:101-102`: `gen_inn12(...) if len>10 else gen_digits_like(...)`. Функция `gen_inn10` существует, объявлена в контракте модуля и **не вызывается нигде, кроме теста**. Проверено исполнением:

```
7707083893 valid=True -> 5603420316 valid=False
```

10-значный ИНН — это ИНН юрлица, то есть **все организации**. Ломает пользовательскую историю «приложение стартует, валидации проходят».

### 6. Коллизия табельных номеров ломает UNIQUE

`mapper.py:286-289` обещает «целое в [lo,hi] БЕЗ коллизий… хэш-в-диапазон запрещён: парадокс дней рождения ломает UNIQUE». `mapper.py:293` делает ровно запрещённое: `y = int(digits) % size`. Проверено:

```
100001  -> 571714
1000001 -> 571714   ← КОЛЛИЗИЯ
```

Плюс `cmd_transformer.py:110` жёстко зашивает диапазон `(100000, 999999)` вместо диапазона колонки. На базе, где табельные выходят за окно, — тихая коллизия и падение UNIQUE на restore.

### 7. Порча текста с обратным слэшем

`postproc.py:251-256` — экранирование и разэкранирование COPY идут в неверном порядке. Проверено:

```
'a\tb' (литеральный слэш + t) -> escape -> unescape -> 'a<TAB>b'   ПОРЧА
```

Уточнение: заявленный случай с возвратом каретки round-trip проходит — формулировку сузить до обратного слэша.

### 8. Связь «зарплата ↔ начисления» разрушается

`executor.py:70-79`: seed перестановки зависит от таблицы и колонки, поэтому `employees.salary` и `payroll.amount` перемешиваются **независимо**. Эксперимент на синтетике с идеальной связью `amount = salary/12`:

```
ДО    corr(зарплата сотрудника, его начисления) = 1.0000
ПОСЛЕ                                          = 0.0590
```

**На демо-базе это не увидеть:** `seed.py:176` генерит `amount` случайно, без связи с `salary`. Дефект латентный — стреляет на боевой базе, где связь есть.

Тем же кодом задето: `SELECT id::text ... ORDER BY id` предполагает колонку `id`. У `contract_items` PK составной — `shuffle` там упал бы. Не стреляет только потому, что ни одна её колонка в стратегии `shuffle` не оказалась.

### 9. NULL превращается в пустую строку

`cmd_transformer.py:61-67`: ветка ФИО отрабатывает **до** проверки NULL. Прогон:

```
вход : middle_name = {'d': None, 'n': True}
выход: middle_name = {'d': '',   'n': False}
```

Тот же механизм для NULL в фамилии и имени. Разъезжается доля NULL, ломаются запросы `WHERE middle_name IS NULL`, при `NOT NULL`-констрейнте — тихая подмена семантики. Верификатор проверок на NULL не имеет.

### 10. `length_policy` — целиком мёртвый код

`postproc.py:233-235`: `max_len = None` жёстко, условие всегда ложно. Ни одно из значений `truncate|widen|fail` не реализовано. Замер на реальных данных: замена адреса даёт **+46 символов** (34 → 80). На `varchar(300)` запас есть, на `comment_text varchar(400)` с несколькими ФИО и адресами переполнение реально. Падать будет на `pg_restore` — **после** того, как верификация показала «зелено».

## P2. Заявленные механизмы отсутствуют физически

### 11. LLM нет ни в одной из четырёх заявленных ролей

Проверено по всем звеньям: клиента нет (grep по `httpx|requests|openai|anthropic|langchain_` — ноль), зависимости нет, `ollama` в compose ни к чему не подключён и `make demo` его **вообще не стартует** (`Makefile:8` поднимает только две БД), `run_pass1` вызывает `prepare_artifacts` **без параметра `llm`** (`executor.py:151`) — то есть `direct`-режим невозможно исполнить с LLM даже при желании.

Дополнительно найдено: `plan_graph.py:64` вызывает `llm_classify` без параметра `ask` (без кэша будет `FileNotFoundError`, а не вызов); `cli.py:108` создаёт `TextSanitizer` без `llm=` — третий эшелон NER всегда возвращает `None`, и каждый неуверенный фрагмент **остаётся неизменённым**; `corpus.llm_components` не вызывается из конвейера вообще.

Единственная `direct`-колонка (`hr.contractors.name`) получает случайное имя из корпуса вместо осмысленной замены. При этом `README.md:11` обещает, что compose поднимает Ollama.

**Это самый крупный разрыв «как задумано / как работает», и он нигде не зафиксирован как отклонение.**

### 12. Presidio отсутствует

Слово встречается в 14 файлах, из них ровно один — код, и это комментарий контракта (`classifier.py:3`). Ни импорта, ни зависимости.

**Скорректировано:** замена сознательна и записана в `design-context.xml:10` («русских распознавателей с контрольными суммами в Presidio нет из коробки»). Дефект не в коде, а в том, что **актуальные документы не обновили**: `solution-design.md` строки 217, 228, 230, 289, 474 и `technology.xml` продолжают заявлять Presidio, включая таблицу лицензий поставляемого OSS и — важнее — обоснование «двух независимых голосов».

### 13. Валидатор корпусов не подключён

`validate_corpus` вызывается только из тестов. `cli.py:89` строит корпуса минуя валидатор. Заявленное в контракте «выход LLM не попадает в базу непроверенным» в коде не обеспечено; проверка длины под колонку-потребитель не работает никогда.

### 14. Гейт публикации — рекомендация, а не механизм

`publishable()` единственный раз употребляется в `cli.py:175` — в `print`. Команды `publish` нет, дамп никуда не перемещается, доступ к каталогу не меняется. Каталог `out/dump/<ts>` читается независимо от значения флага.

## Сборка целого: где оно слабее суммы частей

**Критическое множество** (падает узел — падает всё):

- **M-VERIFIER** — зашит на демо-схему; на чужой базе теряет способность доказать, что инструмент сработал.
- **`tests/fixtures/llm_votes_demo.json`** — без файла голосов планирование невозможно (`FileNotFoundError`). Для новой базы это ручной артефакт на каждую колонку, а CLI по умолчанию подставляет именно демо-фикстуру.
- **`MASTER_SALT`** с молчаливым дефолтом — единственный секрет системы, отсутствие которого не диагностируется.
- **Greenmask** записан в графе частью M-EXECUTOR, но это внешний поставщик: его версия в журнале прогона не фиксируется.

**Слабое звено.** Утверждение «в копии нет ПДн» не может быть сильнее слабейшей проверки. Проверок восемь; ни одна не доказывает, что колонка со стратегией `keep` не содержит персональных данных. Канарейки покрывают 10 заранее известных значений.

**Нарушение монотонности** (`policy.py:140-146`): наследование стратегии классом переписывает `strategy`, не трогая `sem_type`. Эксперимент — КПП унаследовал `fake` от связанной колонки-города и провалился в ветку «название организации»:

```
КПП '770101001' (varchar(9)) -> 'ао уралметиз-д', длина 14  → pg_restore: value too long
```

Валидация молчит: фильтр частотной атаки проверяет только четыре типа, `kpp` в списке нет.

**Порядко-зависимость.** `sanitize_text` — цепочка из шести последовательных замен, где уже заменённые значения подставляются под следующие шаблоны.

**Скрытая связь проходов.** Проход 1 (дочерний процесс Greenmask) и проход 2 (родительский) связаны только переменными окружения. Нет ни одного утверждения, что оба используют одну соль, один корпус и один план. Отпечаток соли в плане закрыл бы это одной строкой.

## Дрейф описания и реализации

1. **Presidio** — в документах и контракте, отсутствует в коде (решение сознательное, документы не обновлены).
2. **LLM** — `requirements.xml` описывает «LLM-агенты производят план и материал замен»; в реализации LLM нет ни в одной точке. Нигде не зафиксировано как отклонение.
3. **Кэш свободного текста «версионируемый артефакт»** (§3.1) → `dict` в памяти, теряется с процессом.
4. **Инициалы наследуют первые буквы фейка полной формы** (§3.2) → реализована только вторая ветка; `test_initials_follow_family` **закрепляет урезанное поведение** — тест зафиксировал дрейф вместо того, чтобы его поймать.
5. **Порог 10 000 — «параметр плана»** (§3.1) → константа модуля; `assign` читает константу, `validate_plan` читает `params` — план и его проверка могут разъехаться.
6. **`docs/module-status.md`** утверждает «критерии §7 измерены». Формально верно, но recall/precision измерялись на базе, из которой вычищены ломающие случаи, а голоса классификатора взяты из заранее написанной фикстуры — это измерение согласованности фикстуры с правилами, не измерение классификации.
7. **`verification/main.xml`** для M-CORPUS и M-RUNLOG приводит доказательства работоспособности функций (`validate_corpus`, `publishable`), которые в конвейере не вызываются. Свидетельство подтверждает способность модуля, а не её использование.
8. После прохода 2 каталог дампа перестаёт соответствовать `metadata.json` Greenmask — восстанавливать можно только `pg_restore`, не `greenmask restore`. Нигде не записано.

## Дополнительно найдено при верификации

- **`_write_sanitization_sql` склеивает SQL из данных без экранирования** (`postproc.py:268`). `pk` берётся из дампа; на базе с текстовым PK апостроф ломает `sanitization.sql`, который исполняется через `psql -f` **на staging**.
- **`rules_detect` объявляет адрес независимо от доли разбора** (`classifier.py:128-129`): порог применяется только позже, в политике. На живом плане видно `reason: addr_parse=0.0` при `sem_type: address` — голос звучит увереннее, чем есть основания, а ветка «свободный текст» для таких колонок недостижима.
- **`verifier._text_columns` подставляет Python-кортеж прямо в SQL** (`verifier.py:176`). Работает случайно: `repr` кортежа из трёх строк совпал с SQL-синтаксисом. Кортеж из одного элемента даст `('text',)` и синтаксическую ошибку.
