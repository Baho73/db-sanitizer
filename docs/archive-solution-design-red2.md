# Санитизация БД: идея, идеология, архитектура

Проектный документ к тестовому заданию РУСАЛ. Фиксирует замысел решения до написания кода.
Дата: 2026-07-30. Редакция 2 (после структурного разбора — см. `design-review.md`, приложение А «решения и альтернативы», приложение Б «разрешённые противоречия»).

---

## 1. Главная идея в одном абзаце

Санитизация — это **не скрипт, а компилятор**. На входе — схема БД, на выходе — план санитизации: декларативный, версионируемый, ревьюируемый человеком артефакт. LLM-агенты работают на **метаданных** и производят этот план плюс материал для замен. Собственно перенос данных — **потоковая трансформация дампа**: `pg_dump` отдаёт `COPY`-поток, замены применяются на лету, `pg_restore` разворачивает уже обезличенную копию. Исходная база при этом не изменяется вообще.

Разделение «медленная умная петля / быстрая тупая петля» — центральное решение всей архитектуры. Из него следуют и масштабируемость, и воспроизводимость, и безопасность.

## 2. Периметр и поток данных

Без этого раздела остальное не имеет смысла: от того, где выполняется процесс, зависит, защищает он данные или сливает их.

```
        ПРОД-КОНТУР (данные не покидают)          │   ВНЕШНИЙ ПЕРИМЕТР
                                                   │
  ┌──────────┐   pg_dump    ┌─────────────────┐   │
  │ прод-БД  │─── поток ───▶│    Greenmask    │   │
  │ (реплика │              │  + наш Cmd-     │   │
  │  или     │   ЧИТАЕТСЯ,  │  трансформер    │   │
  │ снапшот) │   НЕ ПИШЕТСЯ │  (замены здесь) │   │
  └──────────┘              └────────┬────────┘   │
                                     │            │
  ┌──────────────┐                   ▼            │
  │ соль, план,  │           обезличенный   ──────┼──▶  dev / test / аналитика /
  │ корпуса,     │──────────▶  дамп (dir/S3)      │     подрядчик
  │ журнал       │  читаются                      │
  └──────────────┘  здесь и                       │   наружу уходит ТОЛЬКО дамп
   не покидают       только здесь                 │
   контур                                          │
```

Три следствия, каждое из которых снимает риск:

1. **Прод-база только читается.** Нет `UPDATE`, значит нет раздувания таблиц от MVCC, нет взрыва WAL, нет `VACUUM FULL`, нет срабатывания триггеров и записи в аудит-таблицы, нет риска необратимо испортить источник. Второй экземпляр базы прод-объёма не нужен — нужен только диск под выходной дамп.
2. **Соль, корпуса замен и журнал прогонов физически не покидают контур.** Наружу уходит артефакт, из которого обратное отображение невосстановимо.
3. **Вход по ТЗ закрыт полностью.** «Подключение» — штатный режим. «Дамп» — тот же режим против временно развёрнутой копии, либо повторный прогон против уже выгруженного `directory`-дампа.

Хост, на котором работает санитизатор, не имеет исходящего сетевого доступа, кроме явного allowlist (LLM-эндпоинт в контуре, хранилище дампов). Проверяется не строкой в конфиге, а закрытым egress; фактический адрес LLM-провайдера пишется в журнал прогона.

## 3. Идеология: шесть принципов

### 3.1. LLM вызывается на уникальные значения, а не на строки

ТЗ требует: замены генерирует LLM. Прямолинейная реализация вызывает модель на каждую строку — на таблице в 10 млн строк это недели работы, неприемлемые деньги и, что хуже, недетерминированный результат: два прогона дадут две разные базы.

Но соседнее требование ТЗ снимает конфликт само: **замены обязаны быть сквозными**, то есть одно исходное значение всюду заменяется одним и тем же новым. Значит осмысленных вызовов ровно столько, сколько **уникальных значений**, а не строк. Колонка «должность» на 5 млн строк содержит 300 разных значений — 300 вызовов, а не 5 миллионов. Результат идентичен построчному вызову, стоимость меньше в четыре порядка.

Отсюда два режима, выбираемых по кардинальности колонки:

| Режим | Когда | Как работает LLM |
|---|---|---|
| **Прямой** | кардинальность ≤ 10 000 (должность, подразделение, тип документа, город, категория) | LLM получает список уникальных значений и порождает для каждого правдоподобную замену того же уровня и стиля. Результат материализуется в план. Требование ТЗ выполняется буквально и наблюдаемо |
| **Корпусный** | кардинальность > 10 000 (ФИО, адреса, телефоны, email) | LLM порождает взвешенные компоненты (частотные списки фамилий, имён, отчеств, улиц, городов), из которых комбинаторно собирается корпус; привязка исходного значения к элементу корпуса — детерминированная хэш-функция |

Порог 10 000 — параметр плана, не константа кода.

**Почему корпусный режим не является уклонением от требования.** Он вынужден требованием безопасности: LLM не должна видеть настоящие ФИО, адреса и телефоны — иначе обезличивание само становится каналом утечки. Модель физически не может «заменить конкретное ПДн-значение», не увидев его. Поэтому для персональных данных она делает единственное, что безопасно и осмысленно: производит материал замен. Для нечувствительных категорий («Ведущий инженер-технолог») показ исходного значения безопасен — там работает прямой режим.

**Свободный текст** (комментарии, примечания, описания инцидентов) обрабатывается построчно, потому что сущности заранее неизвестны. Первым эшелоном идёт NER, LLM подключается только на фрагментах ниже порога уверенности, батчами, с кэшем по хэшу текста. Цифры и ограничения — в §5.5.

### 3.2. Консистентность через детерминированное отображение, а не через словарь

Требование «одно и то же исходное значение всюду заменяется одинаково» обычно решают таблицей соответствий. На больших базах она не влезает в память, делает процесс stateful и — главное — сама является таблицей реидентификации.

Мы делаем иначе:

```
fake = corpus[ SHA3(salt_effective ‖ normalize(src)) mod |corpus| ]
```

Свойства, которые это даёт:

- **Сквозная консистентность** — по построению, без общего состояния между воркерами.
- **Воспроизводимость** — та же соль, тот же план, тот же корпус дают тот же результат.
- **Параллелизм** — воркерам нечего разделять, потому что таблицы соответствий не существует.
- **В выгружаемом артефакте нет данных для обратного отображения.** Не «необратимость»: при владении солью отображение восстановимо. Поэтому соль — актив уровня прод-секрета, с хранением, ротацией и журналом доступа.

**`normalize()` — не деталь, а несущая конструкция.** Ключом должна быть личность, а не строка. «Петров Иван Иванович» в кадровой таблице и «Петров» в тексте комментария — одна личность и три разных строки; наивное хэширование строки даёт три разных фейка и рушит главную гарантию. Поэтому у каждого семантического типа есть свой ключ идентичности:

| Тип | Ключ идентичности | Замена |
|---|---|---|
| ФИО | кортеж (фамилия, имя, отчество) после лемматизации и приведения регистра; отсутствующие части — пусто | покомпонентная, каждая часть из своего корпуса |
| Телефон | только цифры, приведение к `+7XXXXXXXXXX` | из корпуса, формат исходного восстанавливается |
| Email | нижний регистр, обрезка `+tag`, домен отдельно | локальная часть от фейкового ФИО, домен по своему словарю |
| ИНН / СНИЛС / ОГРН | цифры без разделителей | генерируется из хэша, контрольная сумма досчитывается |
| Адрес | нормализованные компоненты (регион, город, улица, дом) | покомпонентная |

Спецификация `normalize()` для каждого типа входит в план и покрывается тестом «разные формы записи одной сущности → одна замена».

**Отдельно про адреса: грязная адресная строка — это не адрес, а свободный текст.** В реальных базах адрес часто лежит одной строкой с опечатками, произвольным порядком частей и посторонними приписками: «мск, тверскя 5 кв 12, спросить Марью Ивановну, домофон 1234». Покомпонентный разбор такого поля не только ненадёжен — он **опаснее**, чем отсутствие разбора: аккуратно заменив распознанные город и улицу, мы сохраним нераспознанный хвост, а в нём чужое имя, номер квартиры и код домофона.

Поэтому решение обратное интуитивному — не чинить, а не пытаться чинить:

1. Профайлер измеряет **долю значений колонки, разбираемых на компоненты** локальным парсером (внешние сервисы нормализации адресов исключены: туда нельзя отправлять ПДн).
2. Разбирается ≥90% — колонка обрабатывается покомпонентно, как в таблице выше.
3. Разбирается меньше — колонка **переклассифицируется в свободный текст** и уходит в конвейер §5.5. Отдельного решения для неё изобретать не нужно: распознавание сущностей в тексте у нас уже есть, и оно найдёт в этой строке не только адрес, но и имя, и телефон.
4. Если география нужна аналитике только на уровне города или региона — вместо разбора применяется `generalize`: из строки извлекается город по словарю, всё остальное отбрасывается. Самый дешёвый и самый безопасный вариант, и в большинстве случаев его достаточно.

**Нераспознанный остаток исходной строки не сохраняется никогда** — независимо от выбранного пути. Это правило валидации плана, а не рекомендация.

### 3.3. Уникальность обеспечивается структурой значения, а не таблицей соответствий

Проблема, которая обычно и заставляет заводить таблицу соответствий: `UNIQUE`-колонки. Коллизия в корпусе там недопустима.

Но уникальность требуется ровно для **идентификаторов** — email, логин, табельный номер, ИНН, номер договора. А идентификаторы имеют формат, допускающий детерминированную генерацию **напрямую из хэша**, без корпуса и без коллизий:

- ИНН: 10 цифр из хэша + досчитанная контрольная сумма;
- табельный номер: целое из хэша в диапазоне колонки;
- email: транслит фейкового ФИО + короткий суффикс из того же хэша;
- номер договора: формат исходного с подставленными цифрами из хэша.

Правдоподобие-как-текст (ФИО, адрес, название организации) требуется там, где уникальность как раз **не** нужна — однофамильцы есть и в реальной базе.

**Следствие: таблица соответствий из архитектуры удаляется полностью.** Минус компонент, минус общее изменяемое состояние, минус гонки, минус источник недетерминизма, минус актив утечки. Функция при этом выполняется. Разбор этого противоречия — в приложении Б, п. 2.

### 3.4. Отображение стабильно внутри копии и различно между копиями

Если соль одна и вечная, один человек получает один и тот же псевдоним во всех выгрузках всех лет и для всех получателей. Две утёкшие копии складываются, накопленные корреляции резко упрощают реидентификацию. Если соль менять — рушится воспроизводимость, ради которой всё и строилось.

Соль делается **производной**:

```
salt_effective = HMAC(master_salt, recipient_id ‖ generation)
```

- **Внутри одной копии** отображение стабильно — консистентность и воспроизводимость сохранены полностью.
- **Между получателями** отображения независимы — копия подрядчика А и копия подрядчика Б не складываются.
- **Между поколениями** возможна плановая ротация; долгоживущий dev-стенд остаётся в своём поколении и не «переезжает» на новые псевдонимы.
- **Побочный эффект — водяной знак.** По значениям утёкшей копии восстанавливается, чьё это поколение и какой получатель.

`master_salt` живёт в секрет-сторе, `recipient_id` и `generation` пишутся в журнал прогона и в метаданные дампа.

### 3.5. План — это артефакт, а не рантайм-решение

`sanitization-plan.yaml` кладётся в git, ревьюится инженером и офицером по безопасности, переиспользуется на всех последующих прогонах. Пока схема не менялась, LLM между прогонами не нужна вообще. При изменении схемы инструмент показывает **дифф плана** и просит доаппрувить только новые и изменённые колонки.

Это ключ к регулярной эксплуатации большой командой: люди спорят с моделью не каждый раз, а один раз в pull request'е.

Инструмент **fail-closed**, и два случая разведены явно, чтобы их не перепутали в коде:

| Ситуация | Поведение |
|---|---|
| Колонки нет в плане (схема изменилась) | прогон не стартует |
| Колонка в плане со статусом `unresolved` | план не проходит валидацию, до исполнения дело не доходит |
| Колонка в плане со стратегией `null` | выполняется — но только как явный осознанный выбор человека |

### 3.6. Ядро не знает про Postgres

Конвейер описан как **detect → decide → map → apply**. Первые три шага работают с абстракциями (источник, поле, семантический тип, стратегия), `apply` подключается плагином.

Честная формулировка расширяемости: в docx, csv и parquet нет ни таблиц, ни колонок, ни внешних ключей, поэтому план для файловых источников — **другой артефакт с другой адресацией**. Переиспользуются **корпуса, соль и правило отображения** — а этого достаточно, чтобы обезличенный документ был согласован с обезличенной базой: тот же человек получит тот же псевдоним и в таблице, и в файле. Обработка файлов при этом выполняется внутри контура, наружу уходит только результат.

## 4. Выбор технологий

Критерии объявляются до сравнения, одни и те же для всех кандидатов в каждом подразделе.

### 4.1. СУБД: PostgreSQL

*Критерии: полнота интроспекции каталога, наличие профильного OSS-инструментария маскирования, потоковая выгрузка, распространённость.*

Решающий критерий — второй: под PostgreSQL существует сразу несколько зрелых специализированных инструментов обезличивания (см. 4.2), под MySQL и MSSQL сопоставимых нет. Прочие критерии для MySQL 8 закрыты не хуже: FK с правилами каскада, `UNIQUE`/PK и `CHECK` (с 8.0.16) отдаются штатными представлениями `information_schema` — распространённое утверждение о «слабой интроспекции» неверно и в обоснование не берётся.

**Зависимость, которую нужно снять до старта:** если прод заказчика на MSSQL, профильный инструмент отсутствует, и остаётся собственный исполнитель — это другой объём работ. Вынесено в развилки (§8).

### 4.2. Движок исполнения: Greenmask

*Критерии: приём дампа, выгрузка дампа, неразрушающий режим, детерминированные замены, пользовательские трансформеры, обработка свободного текста, требования к правам в БД, зрелость.*

| | **Greenmask** | postgresql_anonymizer | pg_datanymizer | свой на Python |
|---|---|---|---|---|
| Приём/выдача дампа | да, `directory`-формат, поверх `pg_dump`/`pg_restore` | через `pg_dump_anon` | да | писать |
| Неразрушающий режим | да, источник только читается | `anonymize_database()` **уничтожает** исходные данные | да | писать |
| Детерминированные замены | **штатно**: `engine: hash` (SHA-3) + `GREENMASK_GLOBAL_SALT` | `pseudo_*`, корпус не управляется | частично | писать |
| Пользовательские трансформеры | **`Cmd`: внешняя программа через stdin/stdout**, метаданные таблицы первой строкой, форматы json/csv/text, без перекомпиляции | функции на PL/pgSQL внутри БД | шаблоны | — |
| Свободный текст | нет | нет | нет | нужен в любом случае |
| Права в БД | обычный читающий пользователь | требуется `CREATE EXTENSION` | обычный | обычный |
| Дополнительно | `validate` с диффом трансформаций, subset с сохранением целостности, storage `directory`/`s3`, параллелизм | декларативные `SECURITY LABEL` в самой БД | — | — |

**Выбран Greenmask.** Два его свойства совпадают с тем, что документ в предыдущей редакции проектировал самостоятельно: детерминированные замены на хэше и потоковая обработка дампа. Писать это своими руками — прямое нарушение требования ТЗ «разработка с нуля допустима только там, где готовых решений нет». `Cmd`-трансформер закрывает последний пробел: наша семантика (корпуса, покомпонентная замена ФИО, свободный текст) подключается внешним процессом без форка движка.

Ещё три его функции попадают в требования ТЗ напрямую: `validate` даёт готовое сопоставление «до/после», `subset` — выдачу подмножества вместо полной копии, `s3` — хранение копий для регулярной эксплуатации.

Что делаем сами (интеграция, а не переизобретение):
1. LLM-агенты, которые генерируют конфигурацию Greenmask вместо ручной разметки сотен колонок. Это и есть незакрытая инструментом дыра: сам он не знает, какая колонка чувствительна.
2. `Cmd`-трансформер с русскими корпусами, покомпонентной заменой ФИО и обработкой свободного текста.
3. Производная соль по получателю и поколению поверх штатного глобального salt.
4. Верификация результата и журнал прогонов.

*Альтернатива, оставленная в проекте:* `postgresql_anonymizer` — если заказчику нужна маскировка **внутри** БД, декларативно и на постоянной основе (например, чтобы аналитик, подключившись к прод-реплике, видел маски). Это другой сценарий, и там расширение сильнее. В нашем сценарии выгрузки копий оно проигрывает по всем критериям, кроме декларативности. Отдельно: цитировавшаяся ранее функция `anon.dump()` объявлена устаревшей и заменена на `pg_dump_anon`; при использовании расширения нужно фиксировать мажорную версию, 1.x и 2.x различаются несовместимо.

### 4.3. Детекция чувствительных данных: Presidio + русские распознаватели

*Критерии: покрытие типов, расширяемость под РФ-специфику, подключаемый NLP-движок, зрелость.*

`presidio-analyzer` берётся как второй, независимый от LLM детектор. Альтернативы (только Natasha, DeepPavlov, чисто правиловый подход, только LLM) проигрывают по расширяемости и готовности: ни одна не даёт одновременно фреймворк распознавателей, подключаемый NLP-движок и анонимизацию.

Честно про «два независимых голоса»: **входы у детекторов разные.** LLM-классификатор читает имена и типы колонок, Presidio — образцы значений. Это не два взгляда на одно, а два разных источника сигнала, и на худших случаях они слепы одновременно: колонка `f_115` с числовым кодом не распознаётся ни по имени, ни по значению. Такие колонки принудительно получают статус `unresolved`. Прирост полноты от объединения детекторов измеряется на размеченном наборе и заявляется числом, а не лозунгом.

Российские идентификаторы делятся на две группы, и смешивать их нельзя:

| С контрольной суммой — распознаются точно, без модели | Только формат и контекст |
|---|---|
| ИНН (взвешенные коэффициенты), СНИЛС (сумма произведений mod 101), ОГРН/ОГРНИП (остаток от деления на 11 / 13) | **КПП** (9 цифр: код ИФНС + причина постановки + номер), **серия и номер паспорта РФ** (регион по ОКАТО + год бланка + номер 000101–999999) |

Для второй группы точность обеспечивается контекстными якорями — имя колонки, соседние слова «серия», «паспорт», «выдан» — и метрики по ним заявляются отдельно. Иначе распознаватель паспорта либо ловит любые десять цифр подряд и калечит рабочие числовые поля, либо молча пропускает паспорта.

NER для свободного текста — `spaCy ru_core_news_lg` или Natasha; Presidio штатно принимает spaCy как движок.

### 4.4. Генерация значений: Faker даёт форму, LLM даёт содержание

Не сравнение, а разделение труда. Faker (`ru_RU`) обеспечивает **валидные форматы** — телефон с существующим кодом, ИНН со сходящейся контрольной суммой, корректную дату. LLM обеспечивает **правдоподобие и разнообразие** — реалистичные частоты фамилий, осмысленные названия организаций, живые адреса.

Выход LLM никогда не попадает в базу непроверенным. Детерминированный валидатор проверяет: формат, контрольную сумму, отсутствие дублей и — отдельным пунктом — **длину относительно каждой колонки, которая этот корпус использует**. Значение длиннее `varchar(n)` роняет прогон на середине; проверка стоит одну строку кода.

**Принятое решение по идентификаторам с контрольной суммой.** Сгенерированный ИНН, СНИЛС или ОГРН со сходящейся контрольной суммой является технически валидным номером и может случайно совпасть с номером реального человека или организации, не имеющих к базе никакого отношения. Утечки это не создаёт — связи с исходным субъектом нет, — но выбор существует, и он сделан осознанно:

| | Контрольная сумма сходится | Заведомо невалидные диапазоны |
|---|---|---|
| Приложения в dev/test | работают, валидация проходит | часть форм забракует значение |
| Случайное совпадение с реальным номером | возможно | исключено |
| Пригодность копии для работы (требование ТЗ) | полная | ограниченная |

**Выбран первый вариант**: контрольные суммы досчитываются, риск случайного совпадения принимается. Основание — прямое требование ТЗ о пригодности копии для разработки и тестирования: номер, который не проходит валидацию в самом приложении, делает копию непригодной именно там, где она нужна.

Второй вариант остаётся доступным как параметр плана на колонку — если для конкретного поля важнее гарантия несовпадения (например, копия уходит внешнему подрядчику), включается генерация в несуществующем диапазоне.

### 4.5. Агентский фреймворк: LangGraph

*Критерии, объявленные до сравнения: детерминированность маршрута, сохранение состояния между запусками, штатная пауза на решение человека, объём интеграционного кода.*

| Фреймворк | Детерминизм | Persistence | Пауза на человека | Вердикт |
|---|---|---|---|---|
| **LangGraph** | явный граф, детерминированные рёбра | checkpointer | штатный `interrupt` + `Command(resume=…)` | **выбран** |
| CrewAI | агенты договариваются — маршрут плавает | слабее | обходным путём | отклонён |
| AutoGen | то же | слабее | обходным путём | отклонён |
| LlamaIndex Workflows | событийная модель, детерминизм есть | есть | слабее выражена | близкий второй |
| OpenAI Agents SDK / Pydantic AI | детерминизм есть | внешний | нет как первоклассной функции | отклонён |
| Temporal / Airflow | максимальный | максимальный | есть | не агентский каркас; берём как внешний планировщик, но требование ТЗ он не закрывает |

Решающий довод: **аппрув плана человеком — это узел графа, а не костыль вокруг него.** LangGraph даёт паузу с сохранением состояния и продолжение хоть через сутки: нужны checkpointer, `thread_id` и вызов `interrupt()`. Ни один «разговорный» фреймворк этого чисто не даёт.

Контраргумент к собственному выбору, который честнее назвать самому: LLM-фаза по этой архитектуре запускается редко — при изменении схемы, — а рантайм вообще детерминированный. Тащить каркас с checkpointer (которому самому нужен Postgres или Redis) ради пяти узлов, срабатывающих раз в квартал, избыточно. **Каркас взят по прямому требованию ТЗ; из требуемых LangGraph наименее навязчив.** Это точнее, чем изображать техническую неизбежность.

### 5.2. Компоненты и их границы

| Компонент | Что делает | Что знает | Чем проверяется |
|---|---|---|---|
| `profiler` | читает каталог, строит FK-граф и статистику | только SQL-каталог | golden-снимок схемы тестовой БД |
| `classifier` | колонка → семантический тип + уверенность | метаданные и образцы | размеченный набор ≥200 колонок |
| `policy` | тип + ограничения → стратегия | план, не данные | набор кейсов «колонка → ожидаемая стратегия» |
| `fk-closure` | классы связанных колонок | FK-граф и домены значений | синтетические схемы с композитными и мягкими связями |
| `corpus` | тип → замены или компоненты | ничего о прод-базе | валидатор: формат, контрольная сумма, дубли, длина |
| `mapper` | значение → замена | корпус, соль | property-тест: детерминизм, консистентность форм, полное покрытие |
| `executor` | конфиг Greenmask + Cmd-трансформер | план и хранилище | интеграционный прогон + сверка с эталонными контрольными суммами |
| `verifier` | сравнивает до/после | обе копии | **канареечный набор** (см. §5.4) |

`mapper` тестируется без БД, `classifier` — на записанных ответах, без LLM. Это гейт CI: набор тестов должен проходить без запущенных Postgres и LLM.

### 5.3. Стратегии замены

Каждая стратегия соответствует методу обезличивания из приказа Роскомнадзора №140 — это не совпадение, а требование к проекту (см. §6.1).

| Стратегия | Что делает | Метод по приказу РКН №140 | Ограничение |
|---|---|---|---|
| `fake` | значение из корпуса по хэшу | введение идентификаторов | **запрещена при кардинальности < 1000** (см. §5.6); проверяется автоматически при валидации плана |
| `generate` | значение конструируется из хэша по формату | введение идентификаторов | для идентификаторов; даёт уникальность без таблицы соответствий |
| `generalize` | огрубление: дата рождения → 1 января того же года, зарплата → середина дециля | изменение состава или семантики | **тип колонки сохраняется** — иначе ломаются приложения в dev/test; требует отдельного подтверждения на колонку |
| `shuffle` | перестановка значений внутри страты | перемешивание | seed = HMAC(соль, таблица, колонка, версия плана) + `ORDER BY` первичному ключу, иначе недетерминирована |
| `keep` | оставить как есть | — | нечувствительное |
| `null` | обнулить | изменение состава | только явный выбор человека; учитывается верификатором как ожидаемое обнуление, а не как просадка разнообразия |

Четвёртый метод приказа — **декомпозиция** (разбиение массива на части с раздельным хранением) — не используется: он решает ту же задачу на уровне хранения, а не значений, и разрушает пригодность копии для разработки, которой требует ТЗ. Отказ осознанный, а не по недосмотру.

Выбор учитывает ограничения БД: под `UNIQUE` идёт `generate`, а не `fake`; под `NOT NULL` не идёт `null`; под FK стратегия назначается классу целиком.

### 5.4. Верификация

Верификатор — не «сам себе тест». Его проверяет **канареечный набор**: в исходную базу заранее внедряются K известных образцов ПДн разных типов, в том числе внутри JSON, внутри свободного текста и в склеенном виде («Петров И.И., тел. 8-905-…»). Требование: K из K найдено в исходной, 0 из K — в санитизированной.

Проверки прогона:

| Проверка | Критерий |
|---|---|
| Ссылочная целостность | все FK валидны на восстановленной копии |
| Объём | `count(*)` по каждой таблице совпадает |
| Разнообразие | относительная просадка энтропии на колонку ≤10%; расхождение по хи-квадрат для топ-50 значений в пределах порога |
| Отсутствие исходных данных | **ни одно значение из исходной колонки не встречается в санитизированной** — сверка множеств хэшей, поколоночно |
| Канарейки | 0 из K |
| Воспроизводимость | поколоночная контрольная сумма `md5(string_agg(col::text,'' ORDER BY pk))` совпадает между двумя прогонами с одной солью и планом |
| Межколоночные инварианты | возраст ↔ дата рождения, адрес ↔ регион ↔ индекс, дата приёма ↔ дата рождения |

Про «повторный скан детектором ПДн»: он **не может** дать ноль находок и никогда не будет критерием приёмки. Замены по требованию ТЗ правдоподобны, и детектор честно опознает сгенерированное ФИО как ФИО. Работающая проверка — сверка множеств хэшей и канарейки, а не «детектор ничего не нашёл».

### 5.5. Свободный текст: где реальная нагрузка

Это единственное место, где обработка идёт построчно, и именно здесь возникает деградация производительности — не в SQL.

- `ru_core_news_lg` на CPU даёт порядка сотен документов в секунду; 5 млн комментариев — часы. Целевой показатель заявляется и замеряется, а не декларируется.
- Порог уверенности, ниже которого фрагмент уходит в LLM, — **версионируемый параметр плана**, а не константа.
- LLM здесь обязательно локальная (Ollama/vLLM в контуре) — во фрагменте настоящие ПДн. Требуется GPU; это отдельная строка в требованиях к железу.
- Найденные сущности заменяются теми же псевдонимами, что и в структурных колонках — за счёт общего ключа идентичности (§3.2). Изменение длины текста контролируется: политика «обрезать / расширить тип / отказ» задаётся на колонку.
- Качество NER на корпоративных комментариях с опечатками, транслитом и жаргоном заметно ниже, чем на новостном корпусе, на котором модель обучалась. Это измеряется на целевом домене и заявляется как есть.

### 5.6. Что защищает от реидентификации, а что нет

Детерминированное отображение сохраняет частоты. На колонках малой кардинальности (должность, регион, отдел, грейд — 50–500 значений) частотный анализ инвертирует замену тривиально: самое частое значение в копии соответствует самому частому в оригинале, и соль не помогает.

Разрешение (приложение Б, п. 4): проблема возникает только от попытки применить `fake` к категориальной колонке.

- **Нечувствительная категория** (регион, отдел, тип документа) — `keep`. Частоты сохраняются идеально, риска нет: эти значения и так не тайна.
- **Чувствительная категория** (грейд, диагноз, основание увольнения) — скрывать нужно не значение, а **связь значения со строкой**: `shuffle` внутри страты по квази-идентификаторам. Распределение по колонке сохраняется полностью, корреляции первого порядка тоже, привязка к конкретному человеку рвётся.
- `fake` остаётся только для колонок высокой кардинальности, где частотная атака не работает.

### 5.7. Журнал прогонов и возобновляемость

Прогон, упавший на 60%, оставляет дамп, который выглядит готовым. Это самый вероятный сценарий реальной утечки, поэтому состояние прогона материализуется:

```
run_log(run_id, plan_version, salt_generation, recipient_id,
        corpus_version, tool_version, table, status, checksum, ts)
```

Правило: **дамп не публикуется в хранилище, пока не все таблицы в статусе `done`.** Прогон возобновляем по таблицам. Версии плана, соли, корпуса и инструмента пишутся и в журнал, и в метаданные дампа — по любой копии восстанавливается, чем и когда она сделана.

Этот журнал живёт **в контуре** и наружу не уходит — в нём имена таблиц, контрольные суммы и версии соли.

### 5.7.1. Примечания к санитизации — внутри самой копии

Отдельная вещь, которая едет **вместе с копией**: получатель должен знать, где данные обработаны штатно, а где по запасному пути. Иначе аналитик посчитает статистику по колонке адресов, не подозревая, что 12% значений заменены целиком синтетическими строками, а не покомпонентно.

```
schema sanitization:
  notes(run_id, table_name, row_pk, column_name, reason)
  summary(run_id, table_name, column_name, strategy, degraded_rows, total_rows)
```

Коды в `reason`: `address_unparsed` — адрес не разобрался на компоненты; `fallback_freetext` — колонка переклассифицирована в свободный текст; `nulled_unresolved` — поле обнулено; `truncated` — замена не влезла в объявленную длину; `low_confidence_ner` — сущность в тексте распознана ниже порога.

Три решения, которые делают это безопасным и незаметным:

1. **Отдельная схема `sanitization`, а не новые колонки в рабочих таблицах.** Структура исходной базы не меняется ни на байт, FK целы, приложения этой схемы просто не видят. Требование ТЗ о сохранении структуры не нарушено.
2. **Построчные записи пишутся только для деградированных значений** — это меньшинство. Если по колонке деградировало больше половины, построчные записи не пишутся вовсе: колонка отмечается целиком в `summary`, иначе таблица примечаний раздуется до размера самой базы.
3. **Никаких исходных данных в примечаниях** — только код причины. Ни исходного значения, ни его фрагмента, ни длины.

Побочная выгода: `summary` — это готовая часть отчёта «до/после» и материал для улучшения плана. Колонка, у которой из прогона в прогон растёт доля деградаций, — сигнал, что классификация устарела.

## 6. Правовое соответствие, ограничения и остаточные риски

### 6.1. Соответствие 152-ФЗ

Решение проектируется не «в духе закона», а под конкретную норму.

**Ключевое:** определение обезличивания в 152-ФЗ (ст. 3 п. 9) — «действия, в результате которых становится невозможным без использования **дополнительной информации** определить принадлежность персональных данных конкретному субъекту». Оговорка про дополнительную информацию принципиальна: российский закон, в отличие от GDPR, **не требует необратимости**. Существование ключа не выводит результат из-под определения обезличивания.

Более того, приказ Роскомнадзора **№140 от 19.06.2025** (пришёл на смену №996 от 2013 г. и распространяется теперь на всех операторов, а не только на государственные органы) называет первый метод прямо: «введение идентификаторов (**псевдонимизация**)». То есть наша схема — не компромисс между анонимизацией и удобством, а поименованный в нормативном акте метод.

Как выполняются требования:

| Требование | Как закрыто |
|---|---|
| Применяется утверждённый метод обезличивания | все стратегии, кроме `keep`, отображаются на методы приказа №140 (§5.3) |
| Ключ (дополнительная информация) хранится **отдельно** от обезличенных данных | мастер-соль в секрет-сторе прод-контура, в выгружаемый дамп не попадает ни в каком виде (§2) |
| Конфиденциальность процесса обезличивания | процесс исполняется внутри контура, хост без исходящего доступа кроме allowlist, доступ к соли журналируется |
| Сохранение свойств данных, пригодных для дальнейшей обработки | требование ТЗ и наши критерии приёмки совпадают: объём, связи, распределения, межколоночные инварианты (§5.4) |

Что это даёт заказчику практически — с 1 сентября 2025 обезличенные данные:
- обрабатываются **без согласия** субъекта;
- хранятся **без ограничения сроков**;
- **передаются третьим лицам без согласия** — то есть именно тот сценарий, ради которого решение и строится: выдача копий подрядчикам и внешним аналитикам.

Побочная выгода: постановления Правительства №961 от 26.06.2025 и №1154 от 01.08.2025 вводят обязанность оператора по запросу Минцифры обезличить данные и передать их в государственную информационную систему. Тот же инструмент закрывает и эту обязанность — отдельный профиль обезличивания и выгрузка в требуемом составе.

*Оговорка: это инженерная проработка, а не юридическое заключение. Соответствие подтверждает юридическая служба заказчика; документ даёт ей материал — какой метод применён к какому полю и где хранится ключ.*

### 6.2. Остаточные риски и ограничения

Заявляются явно, а не замалчиваются.

- **Реидентификация через квази-идентификаторы остаётся возможной.** Формально требование закона выполнено, но набор «пол + год рождения + город + должность» в принципе позволяет вычислить человека. k-анонимность и l-разнообразие не гарантируются. Ответственный за принятие этого риска назначается заказчиком.
- **Мастер-соль — актив уровня прод-секрета** и одновременно та самая «дополнительная информация» из закона. Хранение в секрет-сторе, ротация по расписанию и при инциденте, журнал доступа. Её компрометация превращает обезличенную копию обратно в персональные данные.
- **Качество зависит от осмысленности имён колонок.** В унаследованных базах с колонками `f_115`, `dop1`, `val3` оба детектора слепы; такие колонки уходят человеку.
- **Мягкие связи между таблицами** (по ИНН без объявленного FK) детектируются эвристикой по вложенности доменов и требуют подтверждения человеком. Пропущенная мягкая связь — реальный риск.
- **Потолок масштаба.** Решение рассчитано на базы до нескольких ТБ; выше — субсетирование перед санитизацией штатным `subset`.
- **Не делается:** своя оркестрация агентов, свой генератор фейков, свой детектор ПДн, свой движок дампа, веб-интерфейс. Поддержка MySQL и MSSQL — абстракция оставлена, реализация по потребности.

## 7. Демонстрация и критерии приёмки

Синтетическая «прод-база» отдела кадров и заявок: 12–15 таблиц, 1–5 млн строк, вложенные и композитные FK, одна мягкая связь без констрейнта, свободнотекстовые комментарии. Враждебные случаи закладываются намеренно:

- колонка `f_115` с числовым кодом — неинформативное имя;
- колонка `city`, в которой лежат полные адреса, — имя врёт;
- `attrs jsonb` с телефонами и ФИО внутри;
- склеенное поле «ФИО, тел. 8-905-…»;
- `UNIQUE`-колонка email и естественный ключ ИНН, участвующий в мягкой связи.

Критерии приёмки (проверяются, а не декларируются):

| Что | Порог |
|---|---|
| Полнота классификации чувствительных колонок | recall ≥0.98, precision ≥0.85 на размеченном наборе ≥200 колонок |
| Канарейки | K из K в исходной, 0 из K в санитизированной |
| Отсутствие исходных значений | пересечение множеств хэшей поколоночно пусто |
| Ссылочная целостность | все FK валидны |
| Объём | `count(*)` совпадает по всем таблицам |
| Разнообразие | просадка энтропии ≤10% на колонку |
| Сквозная консистентность | одна сущность в трёх таблицах в трёх формах записи + в свободном тексте → одна замена |
| Воспроизводимость | поколоночные контрольные суммы двух прогонов совпадают |
| Несвязываемость копий | копии для двух получателей дают разные псевдонимы для одной исходной сущности |
| Производительность | 5 млн строк / 3 свободнотекстовые колонки за ≤45 мин на 8 vCPU, 32 ГБ RAM, 1×GPU; RSS ≤6 ГБ |
| Доля ручного разбора | ≤15% колонок уходит человеку на первом прогоне |

Отчёт «до/после» строится в том числе штатной командой `greenmask validate`, показывающей построчный дифф трансформаций.

## 8. Развилки, требующие подтверждения

По убыванию цены ошибки.

1. **СУБД прод-контура заказчика.** Весь §4.2 предполагает PostgreSQL. Если MSSQL — профильного инструмента нет, объём работ другой.
2. **Где выполняется санитизация и откуда читается источник** — прод-реплика, снапшот или готовый дамп. Влияет на требования к диску, окно обслуживания и согласование с ИБ.
3. **Есть ли в базе JSON-поля, XML, вложения и склеенные текстовые поля.** Адресация плана по JSON-пути — отдельная работа; без неё такие колонки принудительно уходят в `unresolved` и прогон не стартует.
4. **Эксплуатационная модель: кто эти 200 человек** — согласующие план или потребители копий. Во втором случае нужны самообслуживание, параллельные копии, срок жизни копии и отзыв доступа. Документ пока предполагает первое и явно это фиксирует.
5. **Профили обезличивания.** Подрядчику нужна большая глубина, чем внутренней аналитике. Отдельным профилем может стать выгрузка по запросу Минцифры (§6.1). Один план с несколькими уровнями жёсткости или несколько планов.
6. **LLM-провайдер для демонстрации** — локальная модель (честнее по безопасности, медленнее в демо) или внешний API (быстрее). Архитектура поддерживает оба; в проде для ПДн допустима только локальная.
7. **Кто принимает остаточный риск реидентификации** через квази-идентификаторы (§6.2) и кто со стороны заказчика подтверждает соответствие 152-ФЗ.

| А-6 | Управление солью | производная по получателю и поколению | одна вечная соль | одна соль позволяет складывать несколько утёкших копий; производная сохраняет консистентность внутри копии и даёт водяной знак (§3.4) |

## Приложение Б. Журнал разрешённых противоречий

Пять мест, где требования конфликтовали напрямую. Каждое разрешено разведением конфликтующих свойств, а не компромиссом между ними.

**1. Соль должна быть постоянной и переменной.** Постоянной — ради консистентности и воспроизводимости внутри копии. Переменной — иначе несколько утёкших копий складываются и усиливают друг друга. → *Разведение по получателю и по времени:* соль производная, `HMAC(master, recipient ‖ generation)`. Внутри копии постоянна, между копиями различна. Бонусом получился водяной знак, по которому определяется источник утечки. (§3.4)

**2. Таблица соответствий нужна и вредна.** Нужна — для уникальности в `UNIQUE`-колонках. Вредна — общее изменяемое состояние ломает stateless-параллелизм и воспроизводимость, а сама таблица является активом реидентификации. → *Разведение по условию:* уникальность требуется только идентификаторам, а их формат допускает генерацию прямо из хэша, без корпуса и без коллизий. Правдоподобие-как-текст требуется там, где уникальность не нужна. Таблица соответствий удалена из архитектуры целиком. (§3.3)

**3. Корпус должен быть большим и маленьким.** Большим — иначе разнообразие схлопывается и верификатор падает на штатном пути. Маленьким — LLM не сгенерирует миллион значений. → *Разведение по структуре:* LLM генерирует не корпус, а его взвешенные компоненты; корпус получается их произведением. 5000 фамилий × 3000 имён × 1500 отчеств дают миллиарды комбинаций, а веса сохраняют правдоподобные частоты. (§3.1)

**4. Частоты категориальных полей нужно сохранить и скрыть.** Сохранить — их требует аналитика и требование разнообразия. Скрыть — иначе частотный анализ инвертирует замену. → *Разведение по условию:* конфликт возникает только от применения `fake` к категориальной колонке. Нечувствительные категории остаются как есть (частоты идеальны, риска нет), у чувствительных скрывается не значение, а его связь со строкой — перестановкой внутри страты. (§5.6)

**5. LLM должна вызываться на каждое значение и не должна.** Должна — прямое требование ТЗ. Не должна — миллионы вызовов неисполнимы и недетерминированы. → *Разведение по кардинальности:* соседнее требование ТЗ о сквозной консистентности само превращает «на каждое значение» в «на каждое уникальное значение». Для колонок малой кардинальности это буквальное выполнение требования (300 вызовов вместо 5 млн). Для ПДн высокой кардинальности прямой вызов запрещён не экономикой, а безопасностью: показывать модели настоящие ФИО и адреса нельзя. Спорить с заказчиком не о чем — оба режима остаются LLM-генерацией. (§3.1)
