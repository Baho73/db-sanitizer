# Полное ревью проекта db-sanitizer

Дата: 2026-07-31. Метод: чтение нормативных документов (`TZ.md`, `docs/solution-design.md` ред. 4 целиком, README, Makefile), прогон юнит-тестов (118 passed), независимое ревью всех 16 модулей и тестов по зонам, ручная перепроверка ключевых находок по коду и экспериментально. Интеграционные, e2e и `make demo` не запускались (требуют Docker) — их оценка основана на чтении кода.

## Общая оценка

Проект заметно выше типичного уровня тестового задания: продуманная архитектура «компилятор, а не скрипт», честная фиксация отклонений, пять итераций саморазбора с реальными исправлениями, работающая математика ядра. При этом ревью нашло **один блокер, ломающий центральное свойство системы**, и группу major-находок одного рода: **fail-closed семантика надёжно работает на фазе планирования, но имеет пробелы на фазе исполнения**, а ряд заявлений документации опережает код.

## Блокер

**1. Двойная трансформация СНИЛС с дефисами — сквозная консистентность молча сломана.**
`sanitizer/postproc.py:82` заменяет `123-456-789 64` через `gen_snils`, который возвращает 11 цифр подряд (проверено экспериментально: `gen_snils(salt, '12345678964')` → `'3811163743'`); затем `_ID_RUN_RE` (`postproc.py:44,87`) находит эту плоскую строку, видит валидную контрольную сумму и трансформирует **повторно**. Итог: одно значение получает P(P(x)) в пунктуированной записи и P(x) в плоской — и расходится со структурной колонкой. Это прямое нарушение §3.2 проектного документа — свойства, ради которого построена вся формула отображения. Верификатор не ловит (утечки нет — ловить нечем), теста «одно значение в двух форматах → одна замена» нет; `test_snils_canary_from_demo` проходит, проверяя только отсутствие исходника. Лечится форматированием фейка с дефисами либо защитой замены от повторного матча.

## Major

**2. `cmd_run` исполняет план без валидации и без сверки отпечатка схемы.**
`sanitizer/cli.py:105-137` (подтверждено лично): свежий снапшот профилируется (строка 112), но `validate_plan` и сравнение `schema_fingerprint` не вызываются — валидация существует только в `plan_graph` на фазе планирования (`plan_graph.py:105,133`). Колонка, добавленная после аппрува (или план, отредактированный вручную), уедет в дамп сырой: `greenmask_config` формирует трансформации только для колонок плана. §3.5 обещает «колонки нет в плане → прогон не стартует» — на исполнении это не работает; e2e `test_schema_drift_fails_closed` проверяет только повторное планирование, а не `run` со старым планом. Закрывается несколькими строками.

**3. `validate_plan` без белого списка стратегий + `match` без `case _` — fail-open через весь конвейер.**
`sanitizer/policy.py:244-289` нигде не проверяет `strategy`/`sem_type` по белому списку; `sanitizer/cmd_transformer.py:75-91` — `match` без `case _`, неизвестная стратегия молча оставляет значение как есть. Продемонстрировано: стратегия `"fkae"` → валидация возвращает `[]`, значение уезжает нетронутым. Путь реален через `apply_overrides` (`plan_graph.py:58` — белый список полей есть, белого списка значений нет). Верификатор не спасает: построчная `fake(x)!=x` проверяет только `direct/fake/generate` (`verifier.py:128`). Туда же: `_generalize` для любого типа кроме birth_date возвращает исходник (`cmd_transformer.py:148-151`), и валидация это не ловит.

**4. Страховочный слой текста неполон — заявление «100%» ложно.**
`sanitizer/postproc.py:36-44`: `_PHONE_RE` требует литеральный `+7`/`8` — `7 905 123-45-67` не матчится; 10 цифр без префикса отпускаются `_checksummed` без валидной КС; СНИЛС с пробельными разделителями не ловится; кириллические домены email (`ivan@домен.рф`) не ловятся; номера карт (16 цифр > лимита `_ID_RUN_RE` в 15) не покрыты ничем. Если значения нет в структурной колонке плана и в манифесте канареек, утечку не увидит никто. «Глухой промах нейросети на телефоне невозможен» (§5.5) — неверно.

**5. Email без UNIQUE заменяется названием организации.**
`sanitizer/policy.py:193-194` понижает `generate→fake` для email при `not is_unique`, а в `cmd_transformer._fake` нет ветки email — значение попадает в корпус org (`cmd_transformer.py:140-141`). Продемонстрировано: `ivan.petrov@mail.ru` → «ооо вектор». Правдоподобие колонки уничтожено, `reason` в плане не обновляется, путь не покрыт тестами.

**6. Человеческий гейт недостижим из CLI — interrupt/resume работает только в тестах.**
`sanitizer/plan_graph.py:156` (`MemorySaver`), `sanitizer/cli.py:80-89`: при `interrupt` CLI печатает «план ждёт аппрува» и завершается кодом 2 — чекпойнт теряется вместе с процессом. `resume_approved` не вызывается ни из одной команды CLI, только из тестов. Реальный путь аппрува — повторный запуск с `--auto-approve`, и тогда подтверждение помечается `confirmed_by="ci"` (`plan_graph.py:114`), хотя решение принимал человек. Это обесценивает аудит необратимых стратегий и обоснование выбора LangGraph (§4.5: «сохранение состояния между запусками», «продолжение хоть через сутки»). Признано в `design-review-5.md:112`, но нормативный документ не поправлен.

**7. Уникальность email вероятностная, а не структурная.**
`sanitizer/mapper.py:200-208`: защита UNIQUE — 40 бит суффикса; по парадоксу дней рождения при ~10⁶ уникальных адресов вероятность коллизии на UNIQUE — порядка 30% за прогон (падение restore). При этом `policy.py:100-103` включает EMAIL в `_UNIQUE_SAFE` с комментарием «генерация структурно инъективна», а §3.3 обещает идентификаторам генерацию «без коллизий». Для ИНН/СНИЛС/ОГРН (Фейстель) это правда, для email — нет.

**8. `gen_int_like` неинъективен на входах с ведущими нулями.**
`sanitizer/mapper.py:312-338`: cycle-walking биективен на `[10^(n-1), 10^n)` только для входов, уже лежащих в этом множестве. Вход с ведущим нулём шагает «вперёд до ближайшего in-set» и может сойтись с обычным входом из того же сегмента цикла — коллизия воспроизведена экспериментально (1 на 6000 смешанных входов). Докстринг обещает «БЕЗ коллизий» для колонок под UNIQUE — для табельных вида `012345` это неправда.

**9. Составной PK в freetext-таблице → `row_pk` из первой колонки файла.**
`sanitizer/postproc.py:244-247`: при `plan.pk()` бросающем `ValueError` (составной ключ) стоит `except: pk_idx = 0` — прямо против собственного комментария «первой может стоять что угодно, вплоть до персональных данных». В `sanitization.notes.row_pk` (артефакт, уходящий наружу) может уехать исходное ПДн-значение — нарушение правила А-10 «row_pk только пост-трансформационный». Fail-closed здесь обязан ронять прогон.

**10. Проверка `fake(x)≠x` вакуумна для колонок-ключей.**
`sanitizer/verifier.py:126-139`: сверка идёт по PK (`dst_vals.get(pk)`). Если трансформируемая колонка сама входит в PK (сценарий «ключ-ПДн → generate», `policy.py:198-200`), ключи источника в копии не существуют по построению → `get()` возвращает `None` → нарушение не засчитывается никогда. Дополнительно `_pk_expr` через `|| '/' ||` даёт коллизии конкатенации и схлопывание NULL-ключей (`verifier.py:375-394`).

**11. Возобновляемость прохода 2 заявлена (§5.7), но не реализована; падение = потеря файла.**
`sanitizer/postproc.py:250-286`: журнал пишется (`running`/`done`), но `process_dump` журнал не читает — повторный вызов обрабатывает все таблицы заново, повторно заменяя уже заменённые значения (неидемпотентность: фейковый `+7…` матчится `_PHONE_RE` и уходит в следующий фейк). Весь файл читается в память списком строк (на 15 млн текстов из §5.5 — OOM) и перезаписывается на месте без атомарного rename. Тест `test_pass2_resumable_by_table` проверяет только наличие записей в журнале — само свойство не тестируется, потому что его нет.

**12. Переносимость на чужие схемы: SQL-идентификаторы без квотинга; обязательный одноколоночный PK.**
Имена таблиц/колонок интерполируются в f-строки без `psycopg.sql.Identifier`: `profiler.py:156-174`, `executor.py:53,140,176`, `cli.py:166-173`, `verifier.py`. CamelCase, пробелы, зарезервированные слова роняют прогон. Хуже: `_FK_SQL` (`profiler.py:122`) сравнивает `relnamespace::regnamespace::text = %s` — для схемы с квотингом сравнение молча не совпадёт, и FK-граф будет тихо неполным → пропущенные классы эквивалентности → неконсистентные замены. Отдельно: `executor.py:219` безусловно требует `plan.pk(table)` для каждой трансформируемой таблицы, хотя PK нужен только для shuffle — таблица без PK или с составным PK не санитизируется вообще; ограничение недокументировано.

## Документация

**13. `docs/demo-report.md` и `docs/demo-report-dump-input.md` побайтово идентичны и устарели.**
`diff` пуст; оба показывают 8 проверок, канарейки 10/10, эталон «Мельников», ИНН `944226700474`. Актуальные прогоны (`out/verify-report.md`, `out/verify-dump.md`) содержат 11 проверок, 11/11 канареек, эталон «Фомин». Отчёт входа «дамп» — копия отчёта основного входа, чего при двух независимых прогонах быть не может. Сами пути в `Makefile:40,53` с CLI-дефолтами согласованы — претензия только к docs-копиям.

**14. Устаревшие числа тестов.**
README заявляет 103 теста — реально 163 собрано (118 unit + 41 integration + 4 e2e; последние честно скипаются без живых БД). `module-status.md` ведёт историю (103 → 155 → 163), но в строке 111 пишет «155 тестов зелёные» — внутреннее противоречие. `.grace/verification/main.xml` содержит устаревшие числа свидетельств (V-M-MAPPER «13+14», V-M-POSTPROC «10+14+6», «10 канареек» против актуальных 11).

**15. Нормативный `solution-design.md` разошёлся с кодом.**
- §5.7.1: «обвязка правит toc.dat, результат разворачивается штатным pg_restore» — в коде SQL-компаньон `sanitization.sql`, применяемый своей командой `restore` (`postproc.py:324-342`, `cli.py:183-186`). Штатный `pg_restore` опубликованного дампа схему `sanitization` не получит — артефакт не самодостаточен, что противоречит цели раздела («едет вместе с копией»).
- §5.3: «seed = HMAC(соль, таблица, колонка, версия плана)» — код использует seed по группе/сущности (`executor.py:143`), `plan.version` в seed всегда 1.
- §7: критерий «просадка энтропии ≤10%» — код измеряет «≤10% от достижимого» (`verifier.py:160-184`); проверок разбора 5 (идентификаторы по КС, `max_degraded`, целостность не-ПДн текста) в §7 нет, хотя `module-status.md` подаёт их как «измеренные критерии §7».
- §3.2: «инициалы наследуют первые буквы фейка полной формы» — ветки в коде нет (`mapper.py:187-191`); «формат исходного телефона восстанавливается» — `Mapper.phone` всегда отдаёт `+7XXXXXXXXXX` (`mapper.py:193-198`).
- §5.7.1, схема `sanitization`: в коде нет `run_id`, `summary` без разбивки по колонкам/стратегиям, порог 10 000 записей вместо 50% по колонке, два кода причин вместо пяти.
- §5.1: «встроенным трансформерам остаются одиночные технические колонки» — `greenmask_config` встроенных трансформеров не генерирует вовсе (код строже документа).

## Minor (выборка)

- `Salt.version` — мёртвое поле: в HMAC версия не входит (`mapper.py:51-54`); ротация без смены мастер-соли даёт идентичную соль, а журнал честно пишет новую версию — водяной знак и реестр версий §3.4/А-6 деградируют до самодекларации.
- NULL в shuffle-колонке создаёт невалидное состояние протокола Cmd (`executor.py:176-187` → `cmd_transformer.py:188-190`); отпечаток соли проверяется «мягко» (`if expected.exists()`, `cmd_transformer.py:229-230`) — отсутствие файла должно быть отказом.
- Исходные значения утекают в исключения/traceback: `cmd_transformer.py:83,85` (KeyError несёт значение/PK), `:150` (дата в `ValueError`), `executor.py:69-71`.
- Круговое тестирование СНИЛС/ОГРН: gen и valid используют одну формулу, внешних опорных векторов и негативных тестов (`assert not valid_*`) нет — общая ошибка в обоих пройдёт весь набор. ИНН — единственный тип с опорными векторами.
- Раздельные `passport_series`/`passport_number` правилами не детектируются (`classifier.py:79` ловит только слитный формат) — а это схема демо-базы; покрытие только кэшем LLM-голосов при заявленном «контекстном якоре в имени» (§4.3).
- Гейт публикации не связывает verify с содержимым прогона: `publishable()` игнорирует `plan_version`/`master_salt_version`/`recipient_id` из журнала (`runlog.py:63-72`); `column_checksums` пишутся, но ни с чем не сравниваются; `runlog.db` — SQLite без подписи.
- `schema_fingerprint` игнорирует `max_len` (`policy.py:91-97`): сужение `varchar(60)→varchar(10)` не считается дрейфом схемы.
- `json_keys` срезается `LIMIT 50` без `ORDER BY` (`profiler.py:173-175`): недетерминированный отпечаток + тихое зануление ключей вне выборки на исполнении.
- Дизъюнктивные assert'ы в тестах: `test_postproc.py:23` (`or "+7" in out`), `:76` (`assert A or B` при взаимоисключающих исходах), `test_mapper.py:67` — зелёные при ослабленном свойстве.
- Демо-посев недетерминирован между днями: `fake.date_of_birth(minimum_age=…)` считает от `datetime.now()` (`seed.py:131`) при заявленной детерминированности по seed.
- Docker: pip-зависимости без версий, `python:3.12-slim`/`postgres:17` плавают, `postgresql-client` из репозитория дистрибутива может не совпасть с сервером 17 (молчаливый отказ дампа). Зафиксирован только Greenmask `v0.2.22`.
- `report.py` жёстко прошит под демо-схему `hr.*`; на реальной базе HTML-стенд содержал бы исходные ПДн — инструмент это не оговаривает.
- Мёртвый код: `snapshot_json` в plan_graph (реальная зависимость — скрытый модульный `_SNAP_CACHE`, сломается при персистентном чекпойнтере), `confidence_threshold`/`aggressive`-ветка/`import json` в postproc, `llm`-параметр `prepare_artifacts`.
- Голос ADDRESS выдаётся при разбираемости 0.0 (`classifier.py:128-132`); `SemType.PERSON_ID` не возвращается ни одной веткой правил; `endswith("_id")` регистрозависимо.
- Makefile: цель `plan` всегда с `--auto-approve` при комментарии «план с гейтом»; `SUBCOMMANDS` в `test_cli.py:10` не включает `publish`.

## Что сделано хорошо (подтверждено проверкой)

- **Математика ядра верна**: Фейстель биективен (проверено перебором n=1..4), чередование половин и cycle-walking для in-range входов корректны; контрольные суммы ИНН-10/12, СНИЛС (mod 101, края 100/101→00), ОГРН/ОГРНИП (mod 11/13) верны во всех валидаторах и согласованы между проходами.
- **Все утечки разборов 4–5 закрыты в коде подтверждаемо**, с тестами «красный на старом коде» (`test_leak_paths`, `test_data_corruption`, `test_absent_mechanisms`) — проверено по каждой находке, включая враждебные данные (10-значный ИНН, NULL, табельные вне окна).
- **Fail-closed в планировании замкнут end-to-end**: both-blind/disagree → unresolved → валидация → стоп; jsonb без разметки не исполняется; ПДн в direct — отказ валидации; override с белым списком полей, `confirmed`/`confirmed_by` конфигом не подделать (покрыто тестами).
- **Гейт публикации — механизм, а не рекомендация**: отказ без verify, отсутствие созданного каталога, защита от перезаписи — всё протестировано по-настоящему.
- Нераспознанный хвост грязного адреса физически не может уехать в копию (замена целиком + канарейка, юнит- и интеграционный тесты); верификатор доказанно умеет падать (три негативных интеграционных теста с откатом в `finally`); пропущенная проверка ≠ пройденная.
- Соль без умолчаний нигде (compose `:?`, CLI `SystemExit`, Cmd exit 2), производная по получателю/поколению, отпечаток-рукопожатие между проходами, передача дочернему процессу явно.
- Потоковость Cmd-трансформера честная (построчный stdin→stdout, flush, без материализации); протокол Greenmask сверен с документацией и реализован верно; правило единого движка обеспечено структурно (генератор конфига умеет испускать только Cmd).
- LLM-голос не получает образцов ПДн — только метаданные; кэш обязателен офлайн; композитные FK разбираются по позициям через `conkey/confkey WITH ORDINALITY`.
- Комментарии фиксируют причины решений и историю дефектов; `module-status.md` — редкий образец честного статуса («валидация не начиналась»); реальных ПДн в коде, демо и фикстурах нет — только синтетика (Faker/генераторы).

## Итоговая формулировка

Сильная, зрелая работа с редкой честностью документации. Её слабость симметрична силе: механизмы безопасности блестяще спроектированы и подтверждены на фазе планирования, но на фазе исполнения есть fail-open-пробелы, а главная гарантия (сквозная консистентность) сломана ровно в одном месте — на стыке двух regex-слоёв прохода 2. Всё критичное чинится точечно, без пересмотра архитектуры.
