## Итог одним абзацем

Журнал без подписи.

## 2. Новые находки (внесены исправлениями)

### Major

- **Н1. Возобновление прохода 2 в реальном сценарии краха молча ломает консистентность** (найдено независимо тремя ревьюерами, подтверждено лично). Два дефекта складываются: (а) `sanitization-state.json` пишется один раз в конце (`postproc.py:376`), а `runlog.mark("done")` — после каждой таблицы (`:373`); крах между ними → таблица в `already_done`, но не в `summary`, условие пропуска `:315` ложно → повторная обработка; (б) перезапуск CLI создаёт новый `run_id` (`cli.py:191`), `_completed_tables` фильтрует по нему → для прошлого прогона пусто → **полная повторная обработка уже санитизированного дампа**. Воспроизведено: `+79826417636` → `+79584411422` — расходится со структурной колонкой, т.е. «возобновление» воспроизводит исходный дефект двойной трансформации. Тест `test_resume_keeps_previous_notes` переиспользует один run_id и зелёный при сломанном свойстве — тот класс «примерного теста», который разобран в design-review-6. Лечение: запись state после каждой таблицы + возобновление существующего run_id (или сверка отпечатка файла).

- **Н2. `toc_tables` калечит квотированные имена — проход 2 молча пропускает freetext-таблицу** (подтверждено лично). Регэксп `"?([\w]+)"?` (`postproc.py:272`) на выводе `pg_restore -l` для `"Odd Schema"."User Table"` даёт `Odd.Schema`. Дальше таблица не находится в `free_cols` → `continue` — свободный текст уезжает в дамп **несанитизированным, без ошибки и без отметки degraded**. Обратной сверки «все freetext-таблицы плана нашлись в дампе» нет вовсе. Fail-open в главном защитном контуре — иронично на фоне собственной работы команды по квотингу (`ident()`, hostile-тесты). Лечение: отказ на нераспознанной строке TOC + проверка покрытия плана.

- **Н3. Паспорт: один идентификатор — две замены; нестандартные формы утекают.** Детекцию раздельных `passport_series`/`passport_number` добавили, а сквозную консистентность не дотянули: колонки уходят в `gen_digits_like` по 4 и 6 цифрам раздельно, а тот же паспорт в тексте и в `documents.doc_number` — через FPE-10 над «4501 123456». Эксперимент: колонки → «4802 642332», текст → «1705 601316». Демо-база сама содержит такой случай (канареечный сотрудник). Это **тот же класс дефекта, что исходный блокер по СНИЛС**. Плюс формы «4509-123456», двойной пробел, «серия … номер …» в тексте не заменяются вовсе, и верификатор паспорт не контролирует (`wanted` — только INN/SNILS/OGRN). Лечение: ключ идентичности — 10 цифр через одну FPE-10 с разбиением результата; расширить `_PASSPORT_RE`; добавить паспорт в leak-check.

- **Н4. `approve` не связан с тем, что человек читал.** Финализация читает черновик с диска (`Plan.load(draft)`), а не из состояния графа; повторный `plan` на том же thread молча перезапускает граф и перезаписывает и checkpoint, и тот же `.draft.yaml`. Итог: ревьюер читал v1, параллельный запуск записал v2, `approve` подписывает v2 от имени human. Нужна привязка (хэш черновика в payload гейта, сверка в approve).

- **Н5. Гейт публикации удовлетворяется verify-only** — см. «не исправлено» выше; в связке с Н4 обе критические точки (аппрув плана, публикация дампа) держатся на незащищённых файлах в `out/`.

## 5. Итоговая формулировка

Качество исправлений высокое: команда чинит причину, а не симптом, пишет тесты «красные на старом коде» и честно документирует остаток. Но повторное ревью подтверждает системный вывод первого: **слабое место архитектуры — стыки слоёв** (regex-слои текста, колонки↔текст, журнал↔state, гейт↔диск) — там продолжают рождаться дефекты класса «консистентность/полнота рвётся молча» (паспорт, resume, toc). Второй устойчивый паттерн: механизмы работают в штатном и тестовом сценариях, но не в сценарии реального сбоя (resume после краха, approve после параллельного plan, verify с чужим планом). До демонстрации заказчику закрыть Н1–Н3 и остаток находки 2 — все чинятся точечно, без пересмотра архитектуры.

## 6. Рекомендации по исправлению

По каждому пункту: симптом → правка → тест, который обязан быть красным на текущем коде → трудоёмкость (S < 1 ч, M < 1 день, L > 1 дня). Порядок — по приоритету из §4. Общее правило, которое команда уже практикует: правка без теста «красный на старом коде» не считается закрытой.

### 6.1. Н1 — возобновление прохода 2 ломает консистентность (major, M)

**Правка (два независимых изменения):**
1. `postproc.py` — писать `sanitization-state.json` **после каждой таблицы**, атомарно (tmp + `replace`), а не один раз в конце (`postproc.py:376`). Тогда условие пропуска `table in already_done and table in summary` (`:315`) истинно для любой завершённой таблицы в любой точке краха.
2. `cli.py:191` — не порождать новый `run_id` безусловно. Если `work/run_id` существует и в журнале у этого прогона есть `pass2` в статусе `running`/`done` при совпадающем `plan.schema_fingerprint` и отпечатке соли — возобновлять тот же `run_id`; если отпечатки разошлись — отказ с сообщением «другой план/соль — очистите work или используйте новый каталог». Сейчас `_completed_tables` (`postproc.py:383-395`) фильтрует по свежему run_id и для прошлого прогона всегда пуст — resume мёртв вне одного процесса.

**Дополнительная страховка (рекомендуется):** перед повторной обработкой таблицы сверять, что её `.dat.gz` не содержит уже-заменённых значений — дешёвая эвристика: проба N строк, если значение phone-колонки матчится как фейк текущей соли (`fake(x)==x` при подстановке самого себя невозможно, но повторная замена фейка даёт `P(P(x))` — достаточно проверить, что значение не равно `mapper.phone(само_значение)`-подобному) — либо проще: хранить в state per-table хэш файла до/после и при расхождении с фактическим файлом — отказ.

**Тест:** интеграционный, имитирующий крах: обработать таблицу A, записать `mark("done")`, _не_ записывать state (поднять исключение между `:373` и `:376`), затем полный повторный вызов с **новым** run_id — значения таблицы A обязаны остаться байт-в-байт теми же. На текущем коде телефон уезжает в третье значение (воспроизведено ревью). Плюс unit: state переписывается после каждой таблицы, а не в конце.

### 6.2. Н2 — `toc_tables` fail-open на квотированных именах (major, S)

**Правка в `postproc.py:266-274`:**
1. Не распарсенная строка `TABLE DATA` — **отказ**, а не пропуск: если строка матчит `^\d+;.*TABLE DATA`, но не разобралась — `raise`. Молчаливый `continue` здесь недопустим по тому же принципу, по которому колонка вне плана роняет прогон.
2. Разбор квотированных идентификаторов: `"((?:[^"]|"")+)"` с раздвоением кавычек — тот же алгоритм, что в `ident()`, только в обратную сторону. Имена с пробелами/точками/`""` внутри должны давать `Odd Schema.User Table`, а не `Odd.Schema`.
3. **Сверка покрытия:** после построения словаря — `set(free_cols) - set(toc.values())` непусто → отказ с перечислением таблиц. Это закрывает и этот баг, и весь класс «таблица плана потерялась в дампе».

**Тест:** дамп-листинг со строкой `TABLE DATA "Odd Schema" "User Table"` → таблица обработана; отсутствие freetext-таблицы плана в TOC → отказ. Оба красные сейчас.

### 6.3. Н3 — паспорт: один идентификатор, две замены (major, M)

**Правка:**
1. Ключ идентичности паспорта — **10 цифр `series‖number`**, как в текстовом слое. В `plan_graph`/policy пара `passport_series` + `passport_number` одной таблицы объявляется связанной (тот же механизм, что компоненты ФИО в `cmd_transformer._fio_columns`): трансформер собирает 10 цифр, прогоняет **одну** FPE-10 (`gen_digits_like` над десятизначным), результат разбивает 4+6. Колонки поодиночке (если вторая отсутствует в схеме) — текущее поведение + явная запись о деградации.
2. Текстовый слой (`postproc.py:44`): `_PASSPORT_RE` — допустить дефис и произвольные пробельные разделители: `\d{4}[\s-]+\d{6}` плюс форма «серия 4501[,] номер 123456»; замена — через `_reshape` в разделителях исходника (механизм уже есть для СНИЛС).
3. Верификатор (`verifier.py:242-244`): добавить `passport` в `wanted` — собирать `series‖number` из пар колонок и сканировать копию (здесь контрольной суммы нет, поэтому поиск точных вхождений 10 цифр исходника с любым разделителем — алфавит контролёра шире подконтрольного, как уже сделано для СНИЛС).

**Тест:** property «один паспорт в трёх представлениях (две колонки, `doc_number`, текст комментария) → одна и та же 10-значная замена» — прямой аналог `test_snils_same_replacement_in_every_notation`. Негативный: `4509-123456` и `серия 4501 номер 123456` в тексте не переживают прогон.

### 6.4. Остаток находки 2 — обход валидации при сохранённом fingerprint (major, S)

**Правка `policy.py:263-265`:** проверку «все колонки снапшота присутствуют в плане» (`set(by_name) - set(plan.columns)`) вынести из ветки fingerprint-mismatch и выполнять безусловно — fingerprint ловит дрейф схемы, покрытие ловит редактуру плана; это разные проверки, одна не заменяет другую.

**Тест:** план с вручную удалённой колонкой (fingerprint пересчитан/сохранён) → `validate_plan` возвращает ошибку с именем колонки; плюс тест связки `cmd_run → validate_plan` (сейчас её проверяет только e2e повторного планирования, а не `run`).

### 6.5. Н4 — `approve` не привязан к прочитанному черновику (major, M)

**Правка:**
1. В payload гейта (`interrupt`) класть хэш черновика (`sha256(draft.yaml)`); `approve` перед `Command(resume=…)` сверяет хэш файла на диске — расхождение → отказ «черновик изменился после показа, перечитайте».
2. `plan` на треде с ожидающим гейтом — отказ с подсказкой «есть незакрытый гейт: approve или новый `--thread`», вместо молчаливого перезапуска графа с START.
3. Финализация читает план из состояния графа, а не с диска; файл — только витрина для человека.

**Тест:** показать черновик, подменить файл на диске, `approve` → отказ; `plan` поверх висящего гейта → отказ.

### 6.6. Н5 + находка «гейт публикации» — `publishable` не связан с прогоном (major, M)

**Правка `runlog.publishable` + `cmd_verify`:**
1. Требовать полный набор стадий: `pass1=done`, `pass2=done` по всем таблицам плана (а не «все записанные done»), `verify=done`. Пустой журнал с одним `verify=done` публикацию не открывает.
2. `cmd_verify` сверяет свои метаданные (fingerprint плана, отпечаток соли, recipient) с уже записанными строками pass1/pass2 того же `run_id` — расхождение → отказ: verify чужим планом/солью становится видимым, а не зелёным.
3. `column_checksums` получить потребителя: сравнение контрольных сумм проверенного staging с суммами, вычисленными по публикуемому каталогу дампа (или хотя бы сравнение двух прогонов для критерия воспроизводимости — он заявлен в §7 и сейчас не измеряется ничем).
4. (Опционально, следующая итерация) HMAC-подпись записей журнала производной солью — «кто пишет в out/, тот и публикует» перестаёт быть правдой.

**Тесты:** verify-only журнал → отказ; verify с изменённым recipient → отказ; перезапись `run_id`-файла между run и verify → отказ.

### 6.7. Находка 10 — вакуумная `fake(x)≠x` для PK-колонок (major, M)

**Правка `verifier.py:128-142`:** для таблиц, где трансформируемая колонка входит в PK, строки сопоставлять не по PK (его в копии нет), а по стабильному неизменяемому признаку: `row_number() over (order by <оставшиеся непрозрачные колонки или ctid-порядок выгрузки>)` — или проще и надёжнее: для таких колонок заменить построчную проверку на **проверку различия множеств с учётом кратностей** (`group by value having count` источника vs копии — для биективной перестановки мультимножества должны быть дизъюнктны по значениям, что и есть суть `fake(x)≠x` без ложных срабатываний текущей «проверки 3»). Плюс распространить leak-check (3b) с ИНН/СНИЛС/ОГРН на email и person_id — они сейчас вне контроля вообще.

**Тест:** таблица с PK = email (стратегия generate), одна строка намеренно не трансформирована → верификатор красный. Сейчас — зелёный.

### 6.8. NULL в shuffle (major→S)

**Правка `executor.py:190-201`:** `_shuffle_map` — `WHERE {col} IS NOT NULL` (строки с NULL трансформер и так пропускает по флагу `n`). Мультимножество и доля NULL сохраняются.

**Тест:** shuffle-колонка с NULL: доля NULL до/после совпадает, ни одна не-NULL строка не получила `{"d": null, "n": false}`.

### 6.9. `Salt.version` — включить в производную соль (S, но ломает совместимость копий)

**Правка `mapper.py:53-56`:** `effective = HMAC(master, version ‖ recipient ‖ generation)` — как обещают §3.4 и сообщение коммита 38854be. Цена: все ранее выданные копии перестают воспроизводиться на новом коде — принять осознанно (MVP, реальных копий нет) и записать в changelog. Альтернатива — убрать поле и исправить заявления; хуже, потому что ротация без перевыпуска мастера — реальный сценарий эксплуатации.

**Тест:** `Salt(m,'r','g',1).effective != Salt(m,'r','g',2).effective` — красный сейчас.

### 6.10. Страховочный слой: 10-значный телефон, паспортные формы (M)

- Телефон без префикса: 10 цифр в группировке `XXX XXX-XX-XX` с якорем («тел», «моб», начало строки после не-цифры) — заменять через `mapper.phone` с добавлением `+7`. Голые 10 цифр подряд без якоря осознанно не трогать (конфликт с ИНН-10) — и это честно записать в §5.5 вместо «100%».
- Паспорт — см. 6.3.
- «Телефон только с пробелами» (`postproc.py:155`): классифицировать по **группировке**, а не по сплющенным цифрам: `X XXX XXX XX XX` — телефон, `XXX XXX XXX XX` — СНИЛС-кандидат; текущий `strip()` стирает различие.
- §5.5/§7: формулировку «100% телефонов/форматов» заменить перечнем покрытых форматов — проверяемым тестом.

**Тесты:** матрица «формат × ожидаемый обработчик», включая пограничные; доля ложных срабатываний на не-ПДн числах (номера заявок) — ноль.

### 6.12. Прочие точечные (S)

- `verifier.py:436` `_FK_COUNT`: тот же `pg_namespace.nspname = %s`, что в `_FK_SQL`, — сейчас проверка «FK восстановлены» слепнет на квотированной схеме (0==0).
- `_copy_unescape`: добавить `\b \f \v` и восьмеричные `\ooo` (легальные COPY-эскейпы pg_dump); тест round-trip на 0x08.
- `_identifier_leak`: сканировать и числовые колонки (`::text`), не только `_TEXTLIKE`.
- `verify()`: таблица без PK — красная проверка в отчёте, а не исключение, обрывающее весь прогон.
- Исключения без значений: `cmd_transformer.py:83,85`, `mapper.py:335` — завернуть в ошибки с кодом причины, без исходного значения/PK.
- Отказ `gen_int_like` на ведущих нулях — перенести с рантайма на валидацию: `validate_plan` получает от профайлера `min(length)` сэмплов и отклоняет `generate` для такой колонки на гейте, а не посреди дампа.
- `cmd_verify`/`cmd_publish` при отсутствии `run_id` — fail-closed сообщение в стиле остальных команд, не traceback.
- Опечатка в `--confirm` не должна кирпичировать тред: ошибка finalize → гейт перевешивается (повторный `interrupt`), а не потребляется.

### 6.14. Процессные рекомендации (без кода)

1. **Тесты сценария сбоя как класс.** Два ревью подряд дефекты живут в сценарии «крах посередине»: ввести чек-лист «что происходит при kill -9 между любыми двумя строками этой функции» для всех пишущих компонентов (postproc, runlog, executor) и один chaos-интеграционный тест (обрыв контейнера на 60% прохода 2 → перезапуск → верификатор обязан быть зелёным, а значения — не «третьими»).
2. **Матрица представлений для каждого нового типа идентификатора.** Блокер СНИЛС, баг приоритета телефонов и паспортная пара — один паттерн: тип получает несколько текстовых/колоночных представлений, и никто не проверяет, что все они дают одну замену. Правило: новый тип в конвейере не считается подключённым без property-теста «N представлений → одна замена, совпадающая со структурной колонкой».
3. **Демо-база обязана содержать враждебный случай для каждого нового механизма** (как уже сделано для СНИЛС/грязного адреса): паспорт в двух колонках + в тексте, таблица с квотированным именем, таблица без PK, shuffle-колонка с NULL. `test_demo_db_has_hostile_cases` — расширить; рекомендация разбора 6 про пары «колонка↔текст» для телефона/адреса всё ещё не выполнена.
4. **Синхронизация документов — шаг чек-листа коммита**, а не отдельная активность: `solution-design.md` (норматив), README (числа, команды), `module-status.md`, `.grace/verification` — все четыре протухали минимум по разу за две недели.
5. **Регистр «заявлено vs реализовано».** Самые дорогие находки обоих ревью — не баги, а места, где документ/коммит-сообщение утверждало реализованное («версия входит в соль», «возобновляемость реализована», «100% форматов»). Таблица «свойство → где проверяется тестом» в `module-status.md` (частично уже есть) — лучший дешёвый контроль.
