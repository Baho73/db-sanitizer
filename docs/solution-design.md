Проектный документ к тестовому заданию РУСАЛ. Фиксирует замысел решения до написания кода.

## 1. Главная идея в одном абзаце

Санитизация — это **не скрипт, а компилятор**. На входе — схема БД, на выходе — план санитизации: декларативный, версионируемый, ревьюируемый человеком артефакт. LLM-агенты работают на **метаданных** и производят этот план плюс материал для замен. Собственно перенос данных — **два быстрых прохода без LLM в горячем цикле**: потоковая трансформация дампа для структурных колонок, затем дообработка свободнотекстовых таблиц поверх уже выгруженного дампа. Исходная база при этом не изменяется вообще.

Разделение «медленная умная петля / быстрая тупая петля» — центральное решение всей архитектуры. Из него следуют и масштабируемость, и воспроизводимость, и безопасность.

## 2. Периметр и поток данных

Без этого раздела остальное не имеет смысла: от того, где выполняется процесс, зависит, защищает он данные или сливает их.

```
        ПРОД-КОНТУР (данные не покидают)              │   ВНЕШНИЙ ПЕРИМЕТР
                                                       │
  ┌──────────┐  pg_dump   ┌──────────────────────┐    │
  │ прод-БД  │── поток ──▶│ ПРОХОД 1: Greenmask  │    │
  │ (реплика │            │  + наш Cmd-транс-    │    │
  │  или     │  ЧИТАЕТСЯ, │  формер (структурные │    │
  │ снапшот) │  НЕ ПИШЕТСЯ│  колонки)            │    │
  └──────────┘            └──────────┬───────────┘    │
                                     ▼                │
  ┌──────────────┐        ┌──────────────────────┐    │
  │ соль, план,  │        │ ПРОХОД 2: обвязка    │    │
  │ корпуса,     │───────▶│  над дампом (свобод- │    │
  │ журнал, кэш  │ читают-│  ный текст, схема    │    │
  └──────────────┘ ся     │  sanitization)       │    │
   не покидают     только └──────────┬───────────┘    │
   контур          здесь             ▼                │
                          ┌──────────────────────┐    │
                          │ staging-БД: restore  │    │
                          │  + верификация +     │    │
                          │  канарейки           │    │
                          └──────────┬───────────┘    │
                                     ▼                │
                            обезличенный дамп  ───────┼──▶ dev / test / аналитика /
                              (directory / S3)        │    подрядчик
                                                      │  наружу уходит ТОЛЬКО дамп
```

Следствия, каждое снимает свой риск:

1. **Прод-база только читается.** Нет `UPDATE`, значит нет раздувания таблиц от MVCC, нет взрыва WAL, нет срабатывания триггеров, нет риска необратимо испортить источник.
2. **Staging-инстанс — признанная часть сметы, а не скрытая.** Полноразмерная копия прода для трансформации не нужна, но верификация требует restore выгруженного дампа, канарейкам нужно место для записи, а вход «готовый дамп» — временного разворачивания. Всё это один staging-инстанс масштаба выходных данных: диск ≈ объём маскируемых таблиц + сам дамп.
3. **Соль, корпуса, кэш и журнал прогонов физически не покидают контур.** Наружу уходит артефакт, в котором данных для обратного отображения нет.
4. **Оба входа по ТЗ закрыты, но по-разному.** «Подключение» — штатный режим. «Дамп» — разворачивается в staging и обрабатывается как подключение: Greenmask применяет трансформации только при выгрузке из живой БД, повторная обработка готового дампа без разворачивания в его возможности не входит (проверено по документации инструмента).

Хост санитизатора не имеет исходящего сетевого доступа, кроме явного allowlist (LLM-эндпоинт в контуре, хранилище дампов). Закрытость egress подтверждается не строкой в конфиге, а аудитом правил файрвола — при вводе в эксплуатацию и далее по расписанию, ответственный — ИБ заказчика. Фактический адрес LLM-провайдера пишется в журнал каждого прогона.

## 3. Идеология: шесть принципов

### 3.1. LLM вызывается на уникальные значения, а не на строки

ТЗ требует: замены генерирует LLM. Прямолинейная реализация вызывает модель на каждую строку — на таблице в 10 млн строк это недели работы, неприемлемые деньги и, что хуже, недетерминированный результат: два прогона дадут две разные базы.

Но соседнее требование ТЗ снимает конфликт само: **замены обязаны быть сквозными**, то есть одно исходное значение всюду заменяется одним и тем же новым. Значит осмысленных вызовов ровно столько, сколько **уникальных значений**, а не строк. Колонка «наименование контрагента» на 2 млн строк содержит 2 000 разных значений — 2 000 вызовов, а не 2 миллиона. Результат идентичен построчному вызову, стоимость меньше на три порядка.

Режим выбирается по **двум осям — чувствительность И кардинальность**. Одной кардинальности мало: ФИО в базе маленькой компании может иметь 8 000 уникальных значений, и порог по кардинальности отправил бы настоящие ПДн в LLM.

| Режим | Условие | Как работает LLM |
|---|---|---|
| **Прямой** | значение **не является ПДн** И кардинальность ≤ 10 000. Примеры: наименования контрагентов, внутренних проектов, продуктов — то, что надо скрыть, но что не идентифицирует человека | LLM получает список уникальных значений и порождает для каждого правдоподобную замену того же уровня и стиля. Отображение 1:1 материализуется в план. Требование ТЗ выполняется буквально и наблюдаемо |
| **Корпусный** | значение — ПДн (при любой кардинальности) ИЛИ кардинальность > 10 000. Примеры: ФИО, адреса, телефоны, email | LLM порождает взвешенные компоненты (частотные списки фамилий, имён, отчеств, улиц), из которых комбинаторно собирается корпус; привязка исходного значения к элементу — детерминированная хэш-функция |

Порог 10 000 — параметр плана. **ПДн-типы не попадают в прямой режим ни при какой кардинальности** — это правило валидации плана, не рекомендация. Классификация — заслон перед этим правилом, и её ошибка не остаётся незамеченной: материализованные замены прямого режима проходят человеческий гейт, и ревьюер, увидевший в списке «уникальных значений колонки» настоящие ФИО, останавливает план до того, как что-либо ушло в исполнение.

**Почему корпусный режим не является уклонением от требования.** Он вынужден требованием безопасности: LLM не должна видеть настоящие ФИО, адреса и телефоны — иначе обезличивание само становится каналом утечки. Модель физически не может «заменить конкретное ПДн-значение», не увидев его. Поэтому для персональных данных она делает единственное, что безопасно и осмысленно: производит материал замен. Для нечувствительных наименований показ исходного значения безопасен — там работает прямой режим. Категориальные колонки типа «должность» или «регион» чаще всего вообще не нуждаются в замене (`keep`, §5.6) — не всякая колонка малой кардинальности идёт в LLM.

**Свободный текст** (комментарии, примечания, описания инцидентов) обрабатывается построчно, потому что сущности заранее неизвестны. Первым эшелоном идёт NER, LLM подключается только на фрагментах ниже порога уверенности, батчами, с кэшем по хэшу текста. Кэш — версионируемый артефакт наравне с корпусом: без него воспроизводимость свободнотекстовых колонок не существует. Механика и цифры — в §5.5.

### 3.2. Консистентность через детерминированное отображение, а не через словарь

Требование «одно и то же исходное значение всюду заменяется одинаково» обычно решают таблицей соответствий. На больших базах она не влезает в память, делает процесс stateful и — главное — сама является таблицей реидентификации.

Мы делаем иначе:

```
fake = corpus[ SHA3(salt_effective ‖ normalize(src)) mod |corpus| ]
```

Свойства, которые это даёт:

- **Сквозная консистентность** — по построению, без общего состояния между воркерами.
- **Воспроизводимость** — та же соль, тот же план, тот же корпус (и тот же кэш для свободного текста) дают тот же результат.
- **Параллелизм** — воркерам нечего разделять.
- **В выгружаемом артефакте нет данных для обратного отображения.** Не «необратимость»: при владении солью отображение восстановимо перебором кандидатов. Поэтому соль — актив уровня прод-секрета.

**`normalize()` — не деталь, а несущая конструкция.** Ключом должна быть личность, а не строка. «Петров Иван Иванович» в кадровой таблице и «Петров» в тексте комментария — одна личность и разные строки; наивное хэширование строки даёт разные фейки и рушит главную гарантию. Поэтому у каждого семантического типа есть свой ключ идентичности:

| Тип | Ключ идентичности | Замена |
|---|---|---|
| ФИО | кортеж (фамилия, имя, отчество) после лемматизации и приведения регистра; отсутствующие части — пусто. Грамматический род — отдельный признак ключа: «Петров Иван» и «Петрова Анна» — разные кортежи (различаются именем), фейковая фамилия рендерится в роде исходной | покомпонентная, каждая часть из своего корпуса |
| Инициалы | «Петров И.И.» → кортеж (петров, и, и). Согласованность гарантируется **только по фамильному компоненту**: инициалы получаются как первые буквы фейков от однобуквенных ключей. Ветка «наследовать первые буквы фейка полной формы, если она известна из того же класса эквивалентности» в реализацию не вошла — проход 2 работает над дампом и связанной записи в этот момент не видит. Ограничение отражено в критерии приёмки §7 | фамилия из корпуса, инициалы по правилу слева |
| Телефон | только цифры, приведение к `+7XXXXXXXXXX` | из корпуса, всегда в каноническом виде `+7XXXXXXXXXX`. Восстановление исходного формата записи («8 (905) 123-45-67») не реализовано: разбор форматирования не нужен ни одному потребителю копии, а канонический вид проще проверять. Для идентификаторов с контрольными суммами разделители исходника, наоборот, сохраняются — там от них зависит сквозная консистентность записи в разных местах базы |
| Email | нижний регистр, обрезка `+tag`. **Ключ — сам email, фейк — детерминированно из его хэша** (транслит + суффикс). Согласование с фейковым ФИО («kuznetsov@…» у Кузнецова) — только если связь email ↔ ФИО объявлена в плане (колонки в одной таблице, связь подтверждена); иначе замена от контекста строки давала бы разные фейки одному email в разных таблицах | локальная часть из хэша email; при объявленной связи — от фейкового ФИО |
| ИНН / СНИЛС / ОГРН | цифры без разделителей | генерируется из хэша, контрольная сумма досчитывается |
| Адрес | нормализованные компоненты (регион, город, улица, дом) | покомпонентная |

Спецификация `normalize()` для каждого типа входит в план и покрывается тестом «разные формы записи одной сущности → одна замена».

**Отдельно про адреса: грязная адресная строка — это не адрес, а свободный текст.** В реальных базах адрес часто лежит одной строкой с опечатками, произвольным порядком частей и посторонними приписками: «мск, тверскя 5 кв 12, спросить Марью Ивановну, домофон 1234». Покомпонентный разбор такого поля не только ненадёжен — он **опаснее**, чем отсутствие разбора: аккуратно заменив распознанные город и улицу, мы сохраним нераспознанный хвост, а в нём чужое имя, номер квартиры и код домофона.

Поэтому решение обратное интуитивному — не чинить, а не пытаться чинить:

1. Профайлер измеряет **долю значений колонки, разбираемых на компоненты** локальным парсером (внешние сервисы нормализации адресов исключены: туда нельзя отправлять ПДн).
2. Разбирается ≥90% — колонка обрабатывается покомпонентно.
3. Разбирается меньше — колонка **переклассифицируется в свободный текст** и уходит в конвейер §5.5, который найдёт в строке не только адрес, но и имя, и телефон.
4. Если география нужна аналитике только до города — применяется `generalize`: город по словарю, остальное отбрасывается. Самый дешёвый и самый безопасный вариант.

**Нераспознанный остаток исходной строки не сохраняется никогда** — независимо от пути. Проверяется рантайм-канарейкой (§7): в демо-базу кладётся грязный адрес с хвостом, критерий — хвост в копии отсутствует.

### 3.3. Уникальность обеспечивается структурой значения, а не таблицей соответствий

Проблема, которая обычно и заставляет заводить таблицу соответствий: `UNIQUE`-колонки. Коллизия в корпусе там недопустима.

Но уникальность требуется ровно для **идентификаторов** — email, логин, табельный номер, ИНН, номер договора. А идентификаторы имеют формат, допускающий детерминированную генерацию **напрямую из хэша**, без корпуса и без коллизий:

- ИНН: 10 цифр из хэша + досчитанная контрольная сумма;
- табельный номер: целое из хэша в диапазоне колонки;
- email: транслит + суффикс из хэша самого email (§3.2);
- номер договора: формат исходного с подставленными цифрами из хэша.

Правдоподобие-как-текст (ФИО, адрес, название организации) требуется там, где уникальность как раз **не** нужна — однофамильцы есть и в реальной базе.

**Следствие — точная формулировка.** Из архитектуры удалено **разделяемое изменяемое состояние рантайма**: нет компонента, в который воркеры пишут соответствия, нет гонок, нет источника недетерминизма, нет большого актива реидентификации. Статические отображения при этом существуют в одном месте — материализованные 1:1 замены прямого режима в плане (§3.1). Это малые справочники **не-ПДн** значений (≤10 000 строк), они лежат в git, проходят человеческое ревью, и доступ к репозиторию планов ограничен так же, как к самому прод-контуру. Называть их «таблицей соответствий» в смысле угрозы неверно, замалчивать их существование — тоже.

### 3.4. Отображение стабильно внутри копии и различно между копиями

Если соль одна и вечная, один человек получает один и тот же псевдоним во всех выгрузках всех лет и для всех получателей. Две утёкшие копии складываются, накопленные корреляции резко упрощают реидентификацию. Если соль менять — рушится воспроизводимость, ради которой всё и строилось.

Соль делается **производной**:

```
salt_effective = HMAC(master_salt[v], recipient_id ‖ generation)
```

- **Внутри одной копии** отображение стабильно — консистентность и воспроизводимость сохранены полностью.
- **Между получателями** отображения независимы — копии подрядчиков А и Б не складываются.
- **Между поколениями** возможна плановая ротация; долгоживущий dev-стенд остаётся в своём поколении.
- **Мастер-соль версионируется** (`v` в формуле). Ротация заводит новую версию для **новых** поколений; архив старых версий сохраняется в секрет-сторе — иначе умерла бы воспроизводимость и сверяемость всех существующих копий. Честная оговорка: для уже выданных копий ротация ничего не лечит — их отображения зафиксированы навсегда.
- **Водяной знак.** Процедура установления источника утечки: взять несколько известных сущностей прод-базы, перебрать пары (получатель × поколение), вычислить ожидаемые псевдонимы каждой пары и сравнить с утёкшей копией — совпавшая пара и есть источник. Работает при доступе к соли, то есть только изнутри контура.

Версия мастер-соли, `recipient_id` и `generation` пишутся в журнал прогона и в метаданные дампа. Реестр получателей и политику поколений ведёт владелец инструмента (роль назначается заказчиком, по умолчанию — ИБ); без реестра несвязываемость копий превращается в декларацию.

### 3.5. План — это артефакт, а не рантайм-решение

`sanitization-plan.yaml` кладётся в git, ревьюится инженером и офицером по безопасности, переиспользуется на всех последующих прогонах. Пока схема не менялась, LLM между прогонами не нужна для структурных колонок вообще (для свободного текста — см. §5.5: новые тексты требуют NER и, точечно, LLM). При изменении схемы инструмент показывает **дифф плана** и просит доаппрувить только новые и изменённые колонки.

Это ключ к регулярной эксплуатации большой командой: люди спорят с моделью не каждый раз, а один раз в pull request'е.

Инструмент **fail-closed**, и случаи разведены явно, чтобы их не перепутали в коде:

| Ситуация | Поведение |
|---|---|
| Колонки нет в плане (схема изменилась) | прогон не стартует |
| Колонка в плане со статусом `unresolved` | план не проходит валидацию, до исполнения дело не доходит |
| Колонка в плане со стратегией `null` | выполняется — но только как явный осознанный выбор человека |
| ПДн-тип назначен в прямой режим | план не проходит валидацию (§3.1) |

### 3.6. Ядро не знает про Postgres

Конвейер описан как **detect → decide → map → apply**. Первые три шага работают с абстракциями (источник, поле, семантический тип, стратегия), `apply` подключается плагином.

Честная формулировка расширяемости: в docx, csv и parquet нет ни таблиц, ни колонок, ни внешних ключей, поэтому план для файловых источников — **другой артефакт с другой адресацией**. Переиспользуются **корпуса, соль и правило отображения** — а этого достаточно, чтобы обезличенный документ был согласован с обезличенной базой: тот же человек получит тот же псевдоним и в таблице, и в файле. Обработка файлов выполняется внутри контура, наружу уходит только результат.

## 4. Выбор технологий

Критерии объявляются до сравнения, одни и те же для всех кандидатов в каждом подразделе.

### 4.1. СУБД: PostgreSQL

*Критерии: полнота интроспекции каталога, наличие профильного OSS-инструментария маскирования, потоковая выгрузка, распространённость.*

Решающий критерий — второй: под PostgreSQL существует сразу несколько зрелых специализированных инструментов обезличивания (см. 4.2), под MySQL и MSSQL сопоставимых нет. Для MSSQL это проверено, а не предположено: Static Data Masking у Microsoft умер в preview (SSMS 18) и до релиза не дошёл; Dynamic Data Masking — другой механизм (маскирует ответы запросов на живой базе, тривиально обходится и для передачи копий непригоден); зрелые инструменты статического маскирования под MSSQL — только коммерческие (DATPROF, Redgate Data Masker). Прочие критерии для MySQL 8 закрыты не хуже PostgreSQL: FK с правилами каскада, `UNIQUE`/PK и `CHECK` (с 8.0.16) отдаются штатными представлениями `information_schema` — распространённое утверждение о «слабой интроспекции» неверно и в обоснование не берётся.

**Зависимость, которую нужно снять до старта:** если прод заказчика на MSSQL, профильного инструмента нет и остаётся собственный исполнитель — другой объём работ. Вынесено в развилки (§8).

### 4.2. Движок исполнения: Greenmask

*Критерии: приём дампа, выгрузка дампа, неразрушающий режим, детерминированные замены, пользовательские трансформеры, обработка свободного текста, требования к правам в БД, зрелость.*

| | **Greenmask** | postgresql_anonymizer | pg_datanymizer | свой на Python |
|---|---|---|---|---|
| Приём/выдача дампа | выдача — да, `directory`-формат поверх `pg_dump`/`pg_restore`; **приём готового дампа — только через разворачивание в staging** (трансформации применяются при выгрузке из живой БД) | через `pg_dump_anon` | выдача — да | писать |
| Неразрушающий режим | да, источник только читается | в дамп-режиме `pg_dump_anon` — да; статический `anonymize_database()` разрушает источник, но это другой сценарий | да | писать |
| Детерминированные замены | **штатно**: `engine: hash` (SHA-3) + `GREENMASK_GLOBAL_SALT` | `pseudo_*`, корпус не управляется | частично | писать |
| Пользовательские трансформеры | **`Cmd`: внешняя программа через stdin/stdout**, метаданные таблицы первой строкой, форматы json/csv/text, без перекомпиляции | функции на PL/pgSQL внутри БД | шаблоны | — |
| Свободный текст | нет | нет | нет | нужен в любом случае |
| Права в БД | обычный читающий пользователь | требуется `CREATE EXTENSION` | обычный | обычный |
| Зрелость | **молодой проект, версии 0.x** — самый слабый пункт выбранного кандидата; компенсация: используется как прокси над штатными `pg_dump`/`pg_restore`, отказ деградирует до обычного дампа | зрелый (Dalibo, много лет) | заброшен (последние релизы старые) | — |
| Дополнительно | `validate` с диффом трансформаций, subset с сохранением целостности, storage `directory`/`s3`, параллелизм | декларативные `SECURITY LABEL` в самой БД | — | — |

**Выбран Greenmask.** Два его свойства совпадают с тем, что документ в первой редакции проектировал самостоятельно: детерминированные замены на хэше и потоковая обработка дампа. Писать это своими руками — прямое нарушение требования ТЗ «разработка с нуля допустима только там, где готовых решений нет». `Cmd`-трансформер подключает нашу семантику внешним процессом без форка движка.

> **Отклонение реализации: LLM отсутствует физически.** Замысел отводит модели четыре роли — голос классификатора, генерация корпусов, режим `direct`, третий эшелон NER в свободном тексте. В поставленном коде **нет ни одной**: голоса читаются из записанного кэша (`tests/fixtures/llm_votes_demo.json`), корпуса собраны из словарей Faker, третий эшелон всегда возвращает «не знаю» и оставляет неуверенный фрагмент неизменным, а `llm_mode: direct` **не назначается вовсе** — план несёт `params.llm_available: false`, и валидация отклонит план, где этот режим появится. Сама стратегия `direct` при этом работает: карту 1:1 строит детерминированный генератор из корпуса.
>
> Что при этом сохранено: стратегия `direct` (материализованная замена 1:1) существует и работает — карту строит детерминированный генератор из корпуса, а `llm_mode` честно говорит, кто её произвёл. Точки расширения — параметры `llm_classify(ask=…)`, `llm_components(generate=…)`, `prepare_artifacts(llm=…)`, `TextSanitizer(llm=…)` — контрактов не меняют: подключение поставщика не требует правок ни в одном модуле.
>
> Причина отклонения — воспроизводимость демонстрации без сети и без внешних вызовов с персональными данными. Цена — заявленная «независимость двух голосов» на демонстрации не выполняется (§4.3), и это единственное место, где документ и код расходились молча до разбора 4 (находка 11).

**Два ограничения инструмента признаются, а не замалчиваются** (оба проверены по документации): трансформации применяются только при dump с живой БД — поэтому вход «готовый дамп» идёт через staging (§2); добавлять в дамп объекты, которых нет в источнике, Greenmask не умеет — поэтому схему `sanitization` дописывает наша обвязка вторым проходом (§5.7.1).

Что делаем сами (интеграция, а не переизобретение):
1. LLM-агенты, генерирующие конфигурацию Greenmask вместо ручной разметки сотен колонок — незакрытая инструментом дыра: сам он не знает, какая колонка чувствительна.
2. `Cmd`-трансформер с русскими корпусами и покомпонентной заменой ФИО.
3. Обвязка второго прохода: свободный текст, дозапись схемы `sanitization` в directory-дамп.
4. Производная соль по получателю и поколению поверх штатного глобального salt.
5. Верификация результата и журнал прогонов.

*Альтернатива, оставленная в проекте:* `postgresql_anonymizer` — если заказчику нужна маскировка **внутри** БД, декларативно и постоянно (аналитик на прод-реплике видит маски). Это другой сценарий, и там расширение сильнее. Примечание: функция `anon.dump()` устарела, актуален `pg_dump_anon`; при использовании фиксировать мажорную версию — 1.x и 2.x несовместимы.

### 4.3. Детекция чувствительных данных: правила с контрольными суммами (Presidio рассматривался и отклонён)

*Критерии: фреймворк распознавателей (расширяемость под РФ-специфику), подключаемый NLP-движок, готовая анонимизация, зрелость.*

| | **Presidio** | Natasha соло | DeepPavlov | чисто правиловый | только LLM |
|---|---|---|---|---|---|
| Фреймворк распознавателей | **да**, штатное API кастомных recognizers | нет, это NER-библиотека | нет, это NLP-платформа | писать самим | нет |
| Подключаемый NLP-движок | **да** (spaCy/transformers/stanza) | сама и есть движок | сама и есть | — | — |
| Русский NER | через spaCy `ru_core_news_lg` или Natasha как движок | **лучший из коробки** | хороший | нет | хороший, дорогой |
| Детерминизм и цена | детерминирован, дёшев | детерминирован, дёшев | тяжёлый | детерминирован, дёшев | недетерминирован, дорог |

Presidio выбирался как каркас, Natasha/spaCy — как движок внутри него: это не конкуренты, а слои. Чисто правиловый подход остаётся частью решения (распознаватели идентификаторов с контрольными суммами — правила и есть), LLM-only отклонён по цене и недетерминизму.

> **Что реализовано на самом деле.** Presidio в коде **нет**: правиловый голос написан свой. Причина — в таблице выше строка «Русский NER» скрывает главное: распознавателей российских идентификаторов **с проверкой контрольной суммы** (ИНН, СНИЛС, ОГРН) в Presidio из коробки не существует, а именно они дают правиловому голосу точность без контекста. Писать их всё равно пришлось бы; каркас вокруг четырёх регулярных выражений и трёх контрольных сумм — лишний слой. Решение принято при проектировании, но документы до разбора 4 продолжали заявлять Presidio, включая таблицу лицензий поставляемого OSS.
>
> Следствие для «двух независимых голосов» ниже: второй голос — **записанный кэш ответов LLM**, а не работающая модель (см. отклонение в §4.2). На демонстрации это фикстура; независимость входов сохраняется, но независимость **источников** — нет, пока поставщик LLM не подключён.

Честно про «два независимых голоса»: **входы у детекторов разные.** LLM-классификатор читает имена и типы колонок, правиловый детектор — образцы значений. На худших случаях оба слепы одновременно: колонка `f_115` с числовым кодом не распознаётся ни по имени, ни по значению — такие колонки принудительно `unresolved`. Прирост полноты от объединения измеряется на размеченном наборе; критерий в §7.

Российские идентификаторы делятся на две группы, и смешивать их нельзя:

| С контрольной суммой — распознаются точно, без модели | Только формат и контекст |
|---|---|
| ИНН (взвешенные коэффициенты), СНИЛС (сумма произведений mod 101), ОГРН/ОГРНИП (остаток от деления на 11 / 13) | **КПП** (9 цифр: код ИФНС + причина постановки + номер), **серия и номер паспорта РФ** (регион по ОКАТО + год бланка + номер 000101–999999) |

Для второй группы точность обеспечивается контекстными якорями — имя колонки, соседние слова «серия», «паспорт», «выдан» — и метрики заявляются отдельно. Иначе распознаватель паспорта либо ловит любые десять цифр подряд, либо молча пропускает паспорта.

### 4.4. Генерация значений: Faker даёт форму, LLM даёт содержание

Не сравнение, а разделение труда. Faker (`ru_RU`) обеспечивает **валидные форматы** — телефон с существующим кодом, ИНН со сходящейся контрольной суммой, корректную дату. LLM обеспечивает **правдоподобие и разнообразие** — реалистичные частоты фамилий, осмысленные названия организаций, живые адреса.

Выход LLM никогда не попадает в базу непроверенным. Детерминированный валидатор проверяет: формат, контрольную сумму, отсутствие дублей и — отдельным пунктом — **длину относительно каждой колонки, которая этот корпус использует**. Значение длиннее `varchar(n)` роняет прогон на середине; проверка стоит одну строку кода.

**Принятое решение по идентификаторам с контрольной суммой.** Сгенерированный ИНН, СНИЛС или ОГРН со сходящейся контрольной суммой — технически валидный номер и может случайно совпасть с номером реального человека или организации, не имеющих к базе отношения. Утечки это не создаёт — связи с исходным субъектом нет, — но выбор существует и сделан осознанно:

| | Контрольная сумма сходится | Заведомо невалидные диапазоны |
|---|---|---|
| Приложения в dev/test | работают, валидация проходит | часть форм забракует значение |
| Случайное совпадение с реальным номером | возможно | исключено |
| Пригодность копии для работы (требование ТЗ) | полная | ограниченная |

**Выбран первый вариант**: контрольные суммы досчитываются, риск случайного совпадения принимается. Основание — требование ТЗ о пригодности копии: номер, не проходящий валидацию в самом приложении, делает копию непригодной именно там, где она нужна. Второй вариант доступен как параметр плана на колонку — для копий, уходящих внешнему подрядчику.

### 4.5. Агентский фреймворк: LangGraph

*Критерии, объявленные до сравнения: детерминированность маршрута, сохранение состояния между запусками, штатная пауза на решение человека, объём интеграционного кода.*

| Фреймворк | Детерминизм | Persistence | Пауза на человека | Вердикт |
|---|---|---|---|---|
| **LangGraph** | явный граф, детерминированные рёбра | checkpointer | штатный `interrupt` + `Command(resume=…)` | **выбран** |
| CrewAI | агенты договариваются — маршрут плавает | слабее | обходным путём | отклонён |
| AutoGen | то же | слабее | обходным путём | отклонён |
| LlamaIndex Workflows | событийная модель, детерминизм есть | есть | слабее выражена | близкий второй |
| OpenAI Agents SDK / Pydantic AI | детерминизм есть | внешний | нет как первоклассной функции | отклонён |
| Temporal / Airflow | максимальный | максимальный | есть | не агентский каркас; как внешний планировщик — да, требование ТЗ не закрывает |

По четвёртому критерию (объём кода) кандидаты на графе из шести узлов сопоставимы — порядка сотен строк у каждого; решающим он не стал, что честнее, чем изображать различие.

Решающий довод: **аппрув плана человеком — это узел графа, а не костыль вокруг него.** LangGraph даёт паузу с сохранением состояния и продолжение хоть через сутки: checkpointer, `thread_id`, `interrupt()`. Ни один «разговорный» фреймворк этого чисто не даёт.

Контраргумент к собственному выбору, который честнее назвать самому: LLM-фаза запускается редко, рантайм детерминированный; тащить каркас с checkpointer ради пяти узлов раз в квартал избыточно. **Каркас взят по прямому требованию ТЗ; из требуемых LangGraph наименее навязчив.**

Разделение на два прохода — не деталь реализации, а решение двух проблем сразу. Обработка свободного текста занимает часы (§5.5); внутри `Cmd` она держала бы открытыми снапшот и соединение логического дампа всё это время — риск для реплики и нарушение принципа «быстрая тупая петля». Проход 2 работает с файлами уже выгруженного дампа (directory-формат — это сжатые `COPY`-потоки плюс оглавление), транзакция дампа закрыта за минуты. Та же обвязка дописывает в дамп схему `sanitization` — то, чего Greenmask не умеет.

**Правило единого движка.** Все колонки классов эквивалентности и все идентичностные типы (§3.2) обрабатываются только нашим `Cmd`-процессом. Встроенные трансформеры Greenmask не знают `normalize()`: телефон `+7 905…` и `8905…` дали бы у них два разных выхода, тихо сломав консистентность. Встроенным трансформерам оставались бы одиночные технические колонки вне классов (`uuid`, служебные метки времени). **В реализации не осталось и этого:** генератор конфига умеет испускать только `Cmd`, встроенных трансформеров не порождает вовсе. Код строже документа сознательно — так правило единого движка обеспечено структурно, а не дисциплиной.

### 5.2. Компоненты и их границы

| Компонент | Что делает | Что знает | Чем проверяется |
|---|---|---|---|
| `profiler` | читает каталог, строит FK-граф и статистику | только SQL-каталог | golden-снимок схемы тестовой БД |
| `classifier` | колонка → семантический тип + уверенность | метаданные и образцы | размеченный набор ≥200 колонок |
| `policy` | тип + ограничения → стратегия и режим | план, не данные | кейсы «колонка → стратегия», включая «ПДн в прямой режим → отказ» |
| `fk-closure` | классы связанных колонок | FK-граф и домены значений | синтетические схемы с композитными и мягкими связями |
| `corpus` | тип → замены или компоненты | ничего о прод-базе | валидатор: формат, контрольная сумма, дубли, длина |
| `mapper` | значение → замена | корпус, соль | property-тест: детерминизм, консистентность форм, покрытие |
| `executor` | конфиг Greenmask + Cmd-процесс (проход 1) | план и хранилище | интеграционный прогон + эталонные контрольные суммы |
| `postproc` | обвязка прохода 2: свободный текст, дозапись схемы `sanitization`, правка TOC | дамп, кэш, соль | канарейки в тексте + валидность дампа для `pg_restore` |
| `verifier` | сравнивает до/после на staging | обе копии | **канареечный набор** (см. §5.4) |

`mapper` тестируется без БД, `classifier` — на записанных ответах, без LLM. Гейт CI: набор тестов проходит без запущенных Postgres и LLM.

### 5.3. Стратегии замены

Каждая стратегия соответствует методу обезличивания из приказа Роскомнадзора №140 (см. §6.1).

| Стратегия | Что делает | Метод по приказу РКН №140 (прил. 2) | Ограничение |
|---|---|---|---|
| `direct` | материализованная замена 1:1 из плана (прямой режим LLM, §3.1) | введение идентификаторов (п. 2) | **только не-ПДн типы**, кардинальность ≤ порога; сохраняет частоты — допустима, потому что распределение внутренних наименований, в отличие от распределения фамилий, атакующему неизвестно |
| `fake` | значение из корпуса по хэшу | введение идентификаторов (п. 2); вторая опора — п. 4 через способ п. 9(3): «замена на случайные значения атрибутов, не относящихся к субъекту» | **запрещена при кардинальности < 1000** (§5.6): на категориальных колонках частотный анализ инвертирует замену; проверяется при валидации плана |
| `generate` | значение конструируется из хэша по формату | введение идентификаторов (п. 2) | для идентификаторов; уникальность без таблицы соответствий |
| `generalize` | огрубление: дата рождения → 1 января того же года, зарплата → середина дециля | изменение состава или семантики (п. 4) — способ п. 9(1): «обобщённые значения, полученные при округлении… введении порога… укрупнении»; дополнительно квалифицируется как п. 12 | **тип колонки сохраняется**; требует подтверждения на колонку. Верификатор проверяет такие колонки по своим правилам: ожидаемая (сниженная) энтропия и согласованное огрубление зависимых колонок |
| `shuffle` | перестановка значений внутри страты | перемешивание (п. 10) | **двухпроходная**: таблица перестановки предвычисляется в фазе подготовки прогона (осознанное исключение из «потоковой обработки без материализации»); seed = HMAC(соль, **класс эквивалентности сущности**, версия плана), `ORDER BY` первичному ключу. Seed по «таблица+колонка» отклонён после разбора 4: он давал `employees.salary` и `payroll.amount` независимые перестановки, и связь «оклад — его начисления» рвалась (корреляция 1.00 → 0.06). Перестановка строится один раз на группу связанных колонок по объединению значений ключа сущности и сужается на каждую таблицу |
| `keep` | оставить как есть | — | нечувствительное |
| `null` | обнулить | изменение состава или семантики (п. 4) | только явный выбор человека; верификатор учитывает как ожидаемое обнуление |

Методов в приказе **пять**. Не используется один — **декомпозиция** (п. 11, разбиение массива на части с раздельным хранением): он работает с раскладкой хранения, а не со значениями, и разрушает пригодность копии для разработки. Отказ осознанный.

Ограничения БД: под `UNIQUE` идёт `generate`, не `fake`; под `NOT NULL` не идёт `null`; под FK стратегия назначается классу целиком.

### 5.4. Верификация

Верификатор — не «сам себе тест». Его проверяет **канареечный набор**: K известных образцов ПДн разных типов — в том числе внутри JSON, внутри свободного текста, в склеенном виде («Петров И.И., тел. 8-905-…») и грязный адрес с посторонним хвостом. Канарейки внедряются **в staging-копию** до прогона (прод read-only, писать в него нельзя — §2). Требование: K из K найдено в исходной, 0 из K в санитизированной.

Проверки прогона:

| Проверка | Критерий |
|---|---|
| Ссылочная целостность | все FK валидны на восстановленной в staging копии |
| Объём | `count(*)` по каждой таблице совпадает |
| Разнообразие | относительная просадка энтропии на колонку ≤10% **от достижимого**, а не от исходного (для `generalize`/`null` — свои ожидания по плану). Уточнение внесено после разбора 5: замена из корпуса размера *m* по хэшу даёт в среднем *m·(1−e^(−n/m))* различных значений, и при *n*, сравнимом с *m*, просадка неизбежна физически — требовать исходную энтропию значит обещать разнообразие, которого корпус не содержит. Отчёт верификации называет колонки, где предел задан корпусом, и сам предел |
| Идентификаторы источника | ни одно значение ИНН/СНИЛС/ОГРН источника не встречается в копии. Проверка идёт по контрольным суммам и не зависит ни от канареек, ни от форматов, которые умеет распознавать проход 2 |
| Деградации прохода 2 | число фрагментов, оставленных без изменений, не выше порога `params.max_degraded`, объявленного планом и прошедшего гейт. Без объявленного порога верификация не проходит |
| Целостность не-ПДн | фрагменты, персональными данными не являющиеся, доезжают до копии дословно (проверка порчи экранированием и обрезкой) |
| Отсутствие исходных значений | **построчно `fake(x) ≠ x`** для стратегий `direct`/`fake`/`generate` (при совпадении — детерминированное пробирование). `keep`, `shuffle`, `generalize` из проверки исключены явно: они сохраняют исходные значения по построению. Проверка «пересечение множеств пусто» невозможна в принципе — корпус правдоподобных фамилий обязан содержать фамилии, которые есть и в исходной базе |
| Канарейки | 0 из K, включая хвост грязного адреса |
| Воспроизводимость | поколоночная контрольная сумма `md5(string_agg(col::text,'' ORDER BY pk))` совпадает между двумя прогонами с одной солью, планом, корпусом и кэшем |
| Межколоночные инварианты | возраст ↔ дата рождения, адрес ↔ регион ↔ индекс, дата приёма ↔ дата рождения |

Про «повторный скан детектором ПДн»: он **не может** дать ноль находок и не будет критерием приёмки — замены правдоподобны, детектор честно опознает сгенерированное ФИО как ФИО. Работающие проверки — `fake(x)≠x` и канарейки.

### 5.5. Свободный текст: где реальная нагрузка

Единственное место построчной обработки — и единственное, где в фазе исполнения появляется LLM. Обе особенности изолированы в проходе 2 (§5.1): транзакция дампа к этому моменту закрыта.

- Пропускная способность NER: ориентир `ru_core_news_lg` — порядка 200–300 документов в секунду на ядро CPU; при полной параллелизации на 8 vCPU — ~1500–2000 док/с. 15 млн коротких текстов — **2–3 часа**, и это без LLM-хвоста. Числа замеряются на целевом железе и входят в отчёт прогона; критерий §7 задан формулой от объёма, а не одним числом на все случаи.
- Порог уверенности, ниже которого фрагмент уходит в LLM, — версионируемый параметр плана.
- LLM локальная (Ollama/vLLM в контуре) — во фрагментах настоящие ПДн. Требуется GPU; отдельная строка в требованиях к железу и отдельный пункт согласования с ИБ (§8).
- **Кэш ответов NER/LLM по хэшу текста — версионируемый артефакт прогона** наравне с корпусом. Он живёт в контуре, переносится между прогонами и является условием воспроизводимости: без него повторный прогон недетерминирован на текстах. Первый прогон по новым текстам недетерминирован в любом случае — воспроизводимость гарантируется начиная со второго.
- Поверх NER — **страховочный слой правил**: телефоны, email, ИНН/СНИЛС, номера карт ловятся регулярными выражениями и контрольными суммами независимо от NER. Глухой промах нейросети на «8-905-123-45-67» невозможен — формат ловится без неё.
- Найденные сущности заменяются теми же псевдонимами, что и в структурных колонках — общий ключ идентичности (§3.2). Изменение длины текста контролируется политикой на колонку: «обрезать / расширить тип / отказ».
- Качество NER на корпоративных комментариях (опечатки, транслит, жаргон) ниже, чем на новостном корпусе обучения. Замеряется на размеченном наборе целевого домена; порог — в критериях §7, при недостижении порога колонка не считается покрытой.

### 5.6. Что защищает от реидентификации, а что нет

Детерминированное отображение сохраняет частоты. На колонках малой кардинальности (должность, регион, отдел, грейд — 50–500 значений) частотный анализ инвертирует замену тривиально: самое частое значение в копии соответствует самому частому в оригинале, и соль не помогает.

Разрешение (приложение Б, п. 4): проблема возникает только от попытки применить `fake` к категориальной колонке.

- **Нечувствительная категория** (регион, отдел, тип документа) — `keep`. Частоты сохраняются идеально, риска нет.
- **Чувствительная категория** (грейд, диагноз, основание увольнения) — скрывать нужно не значение, а **связь значения со строкой**: `shuffle` внутри страты по квази-идентификаторам.
- `fake` — только на колонках высокой кардинальности.

**Та же атака работает на компонентах ФИО, и это признаётся.** Пофамильное детерминированное отображение сохраняет частоты фамилий, а распределение русских фамилий публично и резко скошено: самая частая фейковая фамилия в копии с высокой вероятностью соответствует Иванову/Смирнову. Это раскрытие квази-идентификатора (не полная реидентификация, но её усилитель). Два уровня ответа:

- по умолчанию — риск фиксируется в §6.2 и принимается назначенным ответственным;
- усиленный профиль — **частотное выравнивание**: фейк выбирается не из всего корпуса, а из ближайшего частотного ранга, ломая ранговое соответствие ценой лёгкого искажения распределения. Параметр профиля обезличивания (§8), не константа.

### 5.7. Журнал прогонов и возобновляемость

Прогон, упавший на 60%, оставляет дамп, который выглядит готовым. Это самый вероятный сценарий реальной утечки, поэтому состояние прогона материализуется:

```
run_log(run_id, plan_version, master_salt_version, salt_generation,
        recipient_id, corpus_version, cache_version, tool_version,
        stage,          -- pass1 | pass2 | verify
        table, status, checksum, ts)
```

Правило: **дамп не публикуется в хранилище, пока верификация не завершена и не все записи в статусе `done`.** Возобновляемость — честно, по стадиям: проход 1 при падении перезапускается целиком (Greenmask dump — единая операция, пофрагментное возобновление не штатно; перезапуск дёшев, потому что проход быстрый); проход 2 возобновляем по таблицам — это наша обвязка, и журнал ведёт она. Версии плана, мастер-соли, корпуса, кэша и инструмента пишутся и в журнал, и в метаданные дампа.

Журнал живёт **в контуре** и наружу не уходит.

### 5.7.1. Примечания к санитизации — внутри самой копии

Отдельная вещь, которая едет **вместе с копией**: получатель должен знать, где данные обработаны штатно, а где по запасному пути. Иначе аналитик посчитает статистику по колонке адресов, не подозревая, что 12% значений заменены целиком синтетическими строками.

```
schema sanitization:
  notes(run_id, table_name, row_pk, column_name, reason)
  summary(run_id, table_name, column_name, strategy, degraded_rows, total_rows)
```

Коды `reason`: `address_unparsed`, `fallback_freetext`, `nulled_unresolved`, `truncated`, `low_confidence_ner`.

**Механизм доставки — явный, потому что штатного нет:** Greenmask не умеет добавлять в дамп объекты, отсутствующие в источнике. Схему дописывает обвязка прохода 2.

> **Как это реализовано (правка оглавления отклонена).** Первая редакция предполагала прямую правку `toc.dat`. От неё отказались: бинарная хирургия над оглавлением хрупка и ломается при смене версии формата. Вместо этого проход 2 кладёт рядом с данными **`sanitization.sql`** — идемпотентный SQL-компаньон, который применяет наша команда `restore` сразу после `pg_restore`.
>
> Цена решения названа прямо: **артефакт перестаёт быть самодостаточным**. Тот, кто развернёт опубликованный каталог штатным `pg_restore` без нашей команды, получит данные без схемы `sanitization` — то есть без примечаний о деградациях. Для контура, где восстановление идёт нашим же инструментом, это приемлемо; для передачи «просто каталога» наружу — нет, и тогда компаньон нужно приложить отдельной инструкцией.

Правила безопасности:

1. **Отдельная схема, а не колонки в рабочих таблицах** — структура базы не меняется, приложения схемы не видят.
2. **`row_pk` — только пост-трансформационное значение.** Если первичный ключ натуральный (ИНН, email), до-трансформационный ключ в примечаниях был бы утечкой в уходящем наружу артефакте.
3. **Построчные записи — только для деградированных значений**; выше 50% деградации по колонке — только сводка в `summary`.
4. **Никаких исходных данных** — только код причины.

Побочная выгода: `summary` — готовая часть отчёта «до/после» и материал сопровождения: колонка с растущей долей деградаций — сигнал, что классификация устарела.

### 5.8. Как выполняются требования ТЗ

| Требование | Как закрыто |
|---|---|
| Приём дампа или подключения | подключение — штатно через Greenmask; дамп — разворачивание в staging и далее как подключение (§2) |
| Правдоподобность замен | корпуса и прямые замены от LLM с учётом локали и частот; валидатор гарантирует формат, контрольные суммы и длину |
| Замены генерирует LLM | прямой режим — буквально, на каждое уникальное не-ПДн значение; корпусный — генерацией материала замен: показывать модели настоящие ПДн запрещено требованием безопасности |
| Сквозная консистентность | хэш-отображение по ключу идентичности; единый `Cmd`-движок для всех классов эквивалентности (§5.1); уникальность — структурной генерацией |
| Ссылочная целостность | FK-замыкание: стратегия назначается классу связанных колонок; верификация постфактум на staging |
| Объём данных | строки не добавляются и не удаляются; сверка `count(*)` |
| Разнообразие | корпус кратно больше кардинальности за счёт комбинаторной сборки; `fake` запрещён на категориальных колонках; энтропийный порог с исключениями по стратегиям |
| Большие объёмы | LLM вне прохода 1; потоковый `COPY`; параллелизм Greenmask; свободный текст — отдельным проходом с кэшем; прод только читается; `subset` для подмножеств. Исключение из «потоковости»: предвычисленные перестановки `shuffle` (§5.3) |
| Расширяемость | ядро `detect → decide → map → apply`; переиспользуются корпуса, соль и правило отображения |
| Воспроизводимость | план в git + производная соль + версионируемые корпус и кэш + версии в журнале + контейнер + одна команда |

## 6. Правовое соответствие, ограничения и остаточные риски

### 6.1. Соответствие 152-ФЗ

Решение проектируется не «в духе закона», а под конкретную норму. Каждое утверждение этого раздела сверено с полнотекстовыми источниками; реквизиты и условия пересмотра — в конце раздела.

**Ключевое:** определение обезличивания в 152-ФЗ (ст. 3 п. 9) — «действия, в результате которых становится невозможным без использования **дополнительной информации** определить принадлежность персональных данных конкретному субъекту персональных данных» (цитата дословная). Оговорка про дополнительную информацию принципиальна: российский закон, в отличие от GDPR, **не требует необратимости**. Существование ключа не выводит результат из-под определения обезличивания.

**Метод — по приказу Роскомнадзора №140 от 19.06.2025** (сменил №996 от 2013 г.; обязателен для операторов при самостоятельном обезличивании; случай обезличивания по требованию Минцифры — п. 9.1 ч. 1 ст. 6 — исключён из его сферы прямо в названии приказа). Первый метод приложения 2 — «введение идентификаторов» (в профессиональном обороте его называют псевдонимизацией, но в тексте приказа этого термина нет). Дословно, п. 2 приложения 2: замена данных на «идентификаторы в виде кода, номера или иного обозначения, имеющего постоянное или переменное значение, **присваиваемые на основании заданных оператором алгоритмов**»; п. 3: ключ, позволяющий сопоставить идентификаторы и исходные данные, «хранится оператором отдельно» и не передаётся третьим лицам.

Это сильнее для нас, чем кажется: старый №996 определял метод через «таблицу (справочник) соответствия», новый №140 прямо допускает **алгоритмическое присвоение**. Вычислимое отображение (§3.2) — это и есть заданный оператором алгоритм; мастер-соль в секрет-сторе, отдельно от данных и без передачи третьим лицам, — буквальное выполнение п. 3.

| Требование приказа №140 | Как закрыто |
|---|---|
| Применяется метод из приложения 2 | стратегии отображаются на методы приказа: п. 2, п. 4, п. 10, п. 12 (§5.3) |
| Определение состава данных до обезличивания | план санитизации: полная опись колонок с типами и стратегиями, аппрув до исполнения (§3.5) |
| Оценка достаточности метода | анализ рисков реидентификации §5.6 и §6.2 — частотные атаки, квази-идентификаторы, профили усиления |
| Ключ хранится **отдельно**, не передаётся третьим лицам | мастер-соль в секрет-сторе прод-контура, в дамп не попадает (§2) |
| Конфиденциальность процесса | процесс в контуре, egress закрыт и аудируется, доступ к соли журналируется |
| Учёт действий по обезличиванию | журнал прогонов §5.7; форму учёта сверить с приказом при внедрении |
| Локальные акты оператора — **по каждому применяемому методу** (прил. 1 требует, в т.ч. правила изменения состава/семантики и алгоритм перестановки для перемешивания) | вне инструмента — обязанность заказчика; план санитизации и версии алгоритмов дают готовый материал для этих актов |

**Правовой статус обезличенных копий — честно.** Нормы, разрешающей свободную передачу обезличенных данных третьим лицам, не существует. Обработка без согласия субъекта опирается на конкретные основания ст. 6: п. 9 ч. 1 — статистические и иные исследовательские цели при обязательном обезличивании; п. 9.1 ч. 1 — цели государственного управления. Передача обезличенных копий подрядчикам для разработки и тестирования под эти пункты **автоматически не подпадает**. Вопрос «перестают ли корректно обезличенные данные быть персональными» в законе прямо не решён; доминирующая позиция регуляторов — обратимо-обезличенные данные остаются ПДн (при этом позиции РКН и Минцифры расходятся между собой). Правовую квалификацию сценария выдачи даёт юридическая служба заказчика — инструмент обеспечивает техническую сторону (метод по приказу, ключ, учёт), а не правовое основание передачи. По достижении целей обработки закон допускает обезличивание как альтернативу уничтожению (ч. 7 ст. 5).

**Контекст ГИС** (не наш основной сценарий): 233-ФЗ от 08.08.2024 ввёл ст. 13.1 — обязанность предоставлять обезличенные данные по требованию Минцифры в государственную систему; ПП №966 определяет порядок направления требования, ПП №961 — формирование составов данных и доступ к ним, ПП №1154 — требования и методы обезличивания для этого случая. Наш инструмент **потенциально применим** и здесь, но соответствие требованиям ПП №1154 не анализировалось — профиль для ГИС является отдельной проработкой (§8).

**Нормативная база и условия пересмотра.** 152-ФЗ в ред. 233-ФЗ от 08.08.2024 (ст. 13.1 действует с 01.09.2025) · приказ РКН №140 от 19.06.2025 (Минюст 31.07.2025 №83110, опубликован 01.08.2025, №0001202508010002, в силе с 01.09.2025) · ПП №961 от 26.06.2025 (№0001202506270025) · ПП №966 от 26.06.2025 · ПП №1154 от 01.08.2025. **Цитаты №140 и №961 сверены с официальной публикацией на publication.pravo.gov.ru** (постранично, включая приложение 2 приказа целиком). Изменение редакции любого из актов, новое разъяснение или практика РКН → пересмотр этого раздела; ответственный — по §8 п. 8.

Два уточнения из официального текста, которых нет во вторичных пересказах:
- **п. 9(3) приложения 2** описывает способ «замены значений атрибутов на случайные значения атрибутов, **не относящихся к субъекту персональных данных**» — это буквально наша корпусная замена (чужое правдоподобное ФИО). У стратегии `fake` две независимые правовые опоры: п. 2 (введение идентификаторов) и п. 4 через способ п. 9(3).
- **п. 12 — дополнительный метод**, применяемый «дополнительно» к методам пп. 2, 4, 10, 11, а не самостоятельный; при этом его способ 3 требует «установления заданного количества различных значений… позволяющего отобразить исходное распределение» — прямая нормативная опора нашего требования разнообразия (§5.4).

*Оговорка: это инженерная проработка, а не юридическое заключение. Соответствие подтверждает юридическая служба заказчика; документ даёт ей материал — какой метод применён к какому полю, где хранится ключ, как ведётся учёт.*

### 6.2. Остаточные риски и ограничения

Заявляются явно, а не замалчиваются.

- **Реидентификация через квази-идентификаторы остаётся возможной.** Набор «пол + год рождения + город + должность» в принципе позволяет вычислить человека; k-анонимность и l-разнообразие не гарантируются. Ответственного назначает заказчик.
- **Частотная инверсия фамильных компонент** (§5.6): ранговое сравнение с публичным распределением фамилий раскрывает вероятные исходные фамилии для верхушки распределения. Принято по умолчанию; усиленный профиль с частотным выравниванием доступен.
- **Уникальность email — вероятностная, а не структурная.** У ИНН, СНИЛС, ОГРН и табельного замена биективна по построению (перестановка Фейстеля), коллизий нет вовсе. У email уникальность держится на 40-битном суффиксе: по парадоксу дней рождения на сотнях тысяч адресов вероятность коллизии перестаёт быть пренебрежимой, и она проявится падением `restore` на ограничении UNIQUE, а не утечкой. Порог для базы масштаба сотен тысяч сотрудников: расширить суффикс до 64 бит — правка в одну строку. §3.3 обещает «без коллизий» именно про идентификаторы с контрольными суммами.
- **Замена может случайно совпасть с исходным значением соседней колонки.** Локальная часть фейкового email собирается из фамильного корпуса по ключу самого email — и в редких случаях совпадает с транслитом настоящей фамилии этой же строки. Замерено на копии: **2 строки из 2001** (`Кабанов` → `kabanov.4wrad67s@…`), что соответствует ожидаемому 1/|корпус|. Проверка `fake(x) ≠ x` этого не ловит: она поколоночная, а совпадение межколоночное. Риск принят: раскрытие неотличимо от шума — в остальных 1999 строках локальная часть содержит фамилию, не имеющую к строке отношения, и проверить догадку по копии нельзя. Устранение потребовало бы передать фамилию строки в генератор email, что сломало бы ключ идентичности email (§3.2) и сквозную консистентность между таблицами.
- **Мастер-соль — актив уровня прод-секрета** и та самая «дополнительная информация» из закона. Секрет-стор, версионирование, ротация (только вперёд — выданные копии она не лечит), журнал доступа. Компрометация соли превращает копию обратно в ПДн — перебором кандидатов.
- **Репозиторий планов — часть контура.** Планы с прямым режимом содержат реальные (не-ПДн, но внутренние) значения; доступ к git ограничивается как к контуру, ревьюеры допущены явно.
- **Качество зависит от осмысленности имён колонок.** `f_115`, `dop1` — оба детектора слепы; такие колонки уходят человеку.
- **Мягкие связи** (по ИНН без объявленного FK) детектируются эвристикой и требуют подтверждения; пропущенная связь — реальный риск.
- **Пропускная способность Cmd-прохода** (сериализация каждой строки во внешний процесс) — замеряется на демо, не предполагается.
- **Потолок масштаба** — базы до нескольких ТБ; выше — `subset` перед санитизацией.
- **Не делается:** своя оркестрация, свой генератор фейков, свой детектор ПДн, свой движок дампа, веб-интерфейс. MySQL/MSSQL — абстракция оставлена, реализация по потребности.

## 7. Демонстрация и критерии приёмки

Синтетическая «прод-база» отдела кадров и заявок: 12–15 таблиц, 1–5 млн строк, вложенные и композитные FK, одна мягкая связь без констрейнта, свободнотекстовые комментарии. Враждебные случаи закладываются намеренно:

- колонка `f_115` с числовым кодом — неинформативное имя;
- колонка `city`, в которой лежат полные адреса, — имя врёт;
- `attrs jsonb` с телефонами и ФИО внутри — **базовая адресация по JSON-пути (плоские ключи первого уровня) входит в объём демо**, иначе колонка блокировала бы прогон по fail-closed и демонстрация не стартовала бы; вложенные структуры и XML — развилка §8;
- склеенное поле «ФИО, тел. 8-905-…»;
- грязный адрес с посторонним хвостом (чужое имя, домофон);
- `UNIQUE`-колонка email и естественный ключ ИНН в мягкой связи.

Критерии приёмки (проверяются, а не декларируются):

| Что | Порог |
|---|---|
| Полнота классификации чувствительных колонок | recall ≥0.98, precision ≥0.85 на размеченном наборе ≥200 колонок |
| Полнота NER на свободном тексте | recall ≥0.85 по сущностям на размеченном наборе целевого домена; телефоны/ИНН/email — 100% через страховочный слой правил (§5.5) |
| Канарейки | K из K в исходной, 0 из K в санитизированной; хвост грязного адреса отсутствует в копии |
| Отсутствие исходных значений | построчно `fake(x) ≠ x` для `direct`/`fake`/`generate`; `keep`/`shuffle`/`generalize` — вне проверки по построению |
| Ссылочная целостность | все FK валидны на восстановленной копии |
| Объём | `count(*)` совпадает по всем таблицам |
| Разнообразие | просадка энтропии ≤10% на колонку (кроме `generalize`/`null` — по плану) |
| Сквозная консистентность | одна сущность в трёх таблицах в разных формах записи + в свободном тексте → одна замена; для инициалов без известной полной формы — согласованность по фамильному компоненту (§3.2) |
| Воспроизводимость | поколоночные контрольные суммы двух прогонов совпадают (при одинаковых соли, плане, корпусе, кэше) |
| Несвязываемость копий | копии двух получателей дают разные псевдонимы одной сущности |
| Производительность, проход 1 | 5 млн строк структурных колонок за ≤45 мин на 8 vCPU, 32 ГБ RAM; RSS ≤6 ГБ |
| Производительность, проход 2 | формула: `объём_текстов / замеренная_пропускная_способность`; ориентир 1500–2000 док/с на 8 vCPU + LLM-хвост на GPU; для 15 млн коротких текстов — ≤4 ч |
| Доля ручного разбора | ≤15% колонок уходит человеку на первом прогоне. Оговорка: демо-база синтетическая и спроектирована той же командой — число на ней является демонстрацией механизма, а не гарантией для реальных баз |
| **Вход «дамп»** | отдельный сценарий демо: `pg_dump` демо-базы → разворачивание в staging → полный конвейер → все критерии выше выполняются. Единственный путь ТЗ, который иначе остался бы без доказательства |
| Правдоподобность | слепая проверка: ревьюеру предъявляются N колонок вперемешку из копии и оригинала; различение не лучше случайного. Дополнительно фиксируется: правдоподобность = форматная валидность (валидатор §4.4) + частотная реалистичность корпуса |

Отчёт «до/после» строится в том числе штатной командой `greenmask validate`, показывающей построчный дифф трансформаций.

### 7.1. Формат сдачи

По разделу «Результат» ТЗ — выбран **репозиторий**, а не стенд:

- исходный код + `docker compose up` одной командой (контейнеры: инструмент, демо-Postgres, staging-Postgres, Ollama);

## 8. Развилки, требующие подтверждения

По убыванию цены ошибки.

1. **Трактовка требования «для генерации замен должна использоваться LLM».** Наша реализация: прямые замены LLM для не-ПДн значений + LLM-генерация материала замен для ПДн (показывать модели настоящие ПДн — канал утечки). Мы считаем это выполнением требования по существу и готовы дополнительно показать на демо буквальный построчный режим на одной небольшой нечувствительной таблице. Подтвердить, что трактовка принимается.
2. **СУБД прод-контура заказчика.** Всё §4.2 предполагает PostgreSQL. Если MSSQL — профильного OSS нет (проверено), объём работ другой.
3. **Где выполняется санитизация и откуда читается источник** — прод-реплика, снапшот или готовый дамп. Влияет на диск, окно обслуживания, согласование staging-инстанса и GPU-хоста с ИБ.
4. **Есть ли в базе вложенные JSON-структуры, XML, вложения-файлы.** Плоские JSON-ключи — в объёме (§7); вложенные структуры и XML — отдельная работа, без которой такие колонки уходят в `unresolved`.
5. **Эксплуатационная модель: кто эти 200 человек** — согласующие план или потребители копий. Во втором случае нужны самообслуживание, параллельные копии, срок жизни, отзыв доступа. Документ предполагает первое и явно это фиксирует.
6. **Профили обезличивания**: подрядчик / внутренняя аналитика / выгрузка в ГИС по №1154; частотное выравнивание фамилий (§5.6) — параметр профиля.
7. **LLM-провайдер для демонстрации** — локальная модель или внешний API. В проде для ПДн допустима только локальная.
8. **Кто принимает остаточные риски** §6.2 (реидентификация, частотная инверсия) и кто подтверждает соответствие 152-ФЗ.

## Приложение Б. Журнал разрешённых противоречий

Пять мест, где требования конфликтовали напрямую. Каждое разрешено разведением конфликтующих свойств, а не компромиссом между ними.

**1. Соль должна быть постоянной и переменной.** Постоянной — ради консистентности и воспроизводимости внутри копии. Переменной — иначе утёкшие копии складываются. → *Разведение по получателю и по времени:* соль производная, `HMAC(master[v], recipient ‖ generation)`. Внутри копии постоянна, между копиями различна. Бонус — водяной знак. Версионирование мастер-соли разводит то же противоречие ещё раз — между ротацией и воспроизводимостью прошлых поколений. (§3.4)

**2. Таблица соответствий нужна и вредна.** Нужна — для уникальности в `UNIQUE`-колонках. Вредна — общее изменяемое состояние ломает stateless-параллелизм и воспроизводимость и само является активом реидентификации. → *Разведение по условию:* уникальность требуется только идентификаторам, а их формат допускает генерацию прямо из хэша. Разделяемое изменяемое состояние удалено; статические 1:1 отображения не-ПДн значений прямого режима остаются в плане под ревью — это осознанная граница, а не отступление. (§3.3)

**3. Корпус должен быть большим и маленьким.** Большим — иначе разнообразие схлопывается. Маленьким — LLM не сгенерирует миллион значений. → *Разведение по структуре:* LLM генерирует взвешенные компоненты, корпус — их произведение. 5000 фамилий × 3000 имён × 1500 отчеств — миллиарды комбинаций с правдоподобными частотами. (§3.1)

**4. Частоты нужно сохранить и скрыть.** Сохранить — требуют аналитика и разнообразие. Скрыть — частотный анализ инвертирует замену. → *Разведение по условию:* нечувствительные категории — `keep` (частоты идеальны, риска нет); у чувствительных скрывается связь значения со строкой (`shuffle` в страте), а не значение. Для фамильных компонент то же противоречие разведено по профилю: по умолчанию частоты правдоподобны и риск принят, в усиленном профиле — частотное выравнивание. (§5.6)

**5. LLM должна вызываться на каждое значение и не должна.** Должна — требование ТЗ. Не должна — миллионы вызовов неисполнимы, а показывать модели ПДн нельзя. → *Разведение по чувствительности и кардинальности:* для не-ПДн малой кардинальности требование выполняется буквально (прямой режим); для ПДн LLM генерирует материал замен — запрет тут диктует безопасность, а не экономика. Трактовка вынесена на подтверждение заказчику (§8, п. 1) с готовой демонстрацией буквального режима. (§3.1)
